## По В1: выборочная проверка — да, до Task 005

Проверить 2–3 ячейки вручную. Цель: убедиться, что тематическая schema 3A даёт связный контекст (альтернативные пути допуска, развилки между тестами, взаимосвязи), а не перечень значений параметров в тематических обёртках. Если контекста нет — Фаза 2 не сформирует качественный промпт для 3P.

Рекомендуемые ячейки для проверки: HKEX Main Board equities (простая, хорошо документирована), LSE Main Market equities (сложная, реформа UKLR 2024), что-нибудь по bonds или funds (проверить, нет ли перекоса в сторону equities).

## По В2: 3D — подтверждаю, в пилоте не нужен

Все secondary listing в пилоте — Case 2 (distinct regime), обрабатываются стандартными 3A/3B/3C. Case 1 (пониженные пороги) не встретился. 3D реализовывать при масштабировании, когда появится реальный Case 1.

## По В3: не вводить `admission_category`

Проблема уже решена разделением вопросов A и B в промпте уровня 2 (патч patch_systemic_classification_fix). ESCC, CEF, Debt — это организация rulebook по классам инструментов, не tier и не segment. Flat structure = `tiers: none`. Добавление четвёртого типа сущности усложнит промпты без выигрыша.

---

## По В4: контекстный блок и rulebook_chapters

Контекстный блок в промптах L3 (venue/tier/operator) — не блокирует Task 005 по пилоту, но нужен до масштабирования.

`rulebook_chapters` пустой — не блокирует 3P (контекст для 3P берётся из Фазы 2, не из venue_card). Желательно исправить до масштабирования, не критично для пилота.

## По В5: сначала полный цикл на пилоте

Согласен. Фаза 2 (LLM-маппинг) и 3P (целевой запрос по параметрам) — непроверенные звенья. Валидировать на пилотных данных до тиражирования.

## Дополнение: legacy-ячейки

Не тратить ресурсы на поддержку legacy-алгоритмов из ранних итераций пилота. Если ячейки были обработаны по устаревшей схеме (параметрическая schema 3A, некорректная классификация venue/tier, и т.д.) — отбросить и переделать по актуальной архитектуре. Пайплайн активно корректируется, тянуть за собой результаты, полученные на старых промптах и схемах, бессмысленно — они не совместимы с текущей логикой постобработки.

Конкретно: если среди 74 L3-задач есть результаты, полученные до патча тематической schema 3A — не пропускать их через Фазу 2. Перезапустить с актуальной schema.

---

## Дополнение: ATT-only ячейки

Если среди 26 пилотных ячеек есть ATT-only (admission_path: "trading_only") — промпты 3A/3B/3C для них должны ссылаться на Admission and Disclosure Standards (LSE), а не на UK Listing Rules (FCA). Это разные rulebook, разный надзорный орган. Проверить, что LLM при формировании промптов учитывает admission_path.

---

## Дополнение: legacy-ячейки (в смысле grandfathering)

Отдельный вопрос — ячейки с `legacy=true` (переходные категории, закрытые для новых эмитентов, типа UKLR Equity Shares — Transition). По ним из L3-запросов нужны 3B (поддержание, приостановка, исключение) и 3C (мониторинг), но не 3A (первичный допуск — туда никто не подаёт). В пилоте по таким ячейкам запущен только 3A — это известное расхождение. Для пилота не блокер (отрабатываем пайплайн, не конечный результат). При масштабировании: логику генерации промптов для legacy-ячеек исправить — legacy → 3B + 3C, без 3A.

# Спецификация: Phase 2 → 3P → Pass 2

**Дата:** 2026-03-11  
**От:** Архитектор пайплайна  
**Кому:** Tech Lead  
**Контекст:** Pass 1 выполнен по 17 группам (UK + Гонконг). Словарь параметров обновлён разработчиком ядра (П01–П35+). Далее — генерация промптов 3P, запуск 3P, извлечение значений.

---

## 1. Общая последовательность

```
[СДЕЛАНО] Pass 1 — извлечение фреймворка параметров из обзоров
    ↓
Классификация UNKNOWN_PARAM (в той же диалоговой цепочке)
    ↓
Оценка необходимости доразведки + генерация промптов 3P
    ↓
Запуск 3P через Parallel API
    ↓
Pass 2 — извлечение значений из {3A+3B+3C+3P} по ячейкам
    ↓
Пакетная постобработка
```

Ключевое: **Pass 1, классификация UNKNOWN и генерация промптов 3P выполняются в одной диалоговой LLM-цепочке** (один диалог на группу). Это сохраняет контекст: LLM видит исходные данные, свой собственный Pass 1 и критерии доразведки одновременно.

---

## 2. Диалоговая цепочка (один диалог на группу)

Для каждой из 17 групп (jurisdiction × market_type × instrument_class × admission_path_type) — один LLM-диалог из 5 сообщений.

### Сообщение 1 (system)

Содержит:

**А. Словарь параметров** (полный, П01–П35 + все категории). Каждый параметр — ID, название, краткое определение.

**Б. Правила классификации UNKNOWN_PARAM:**

```
When you encounter a parameter not in the dictionary:

CATEGORY A — "Maps to existing": the parameter is a reformulation 
or sub-aspect of an existing dictionary parameter. 
Example: "minimum market cap of free float" = П03.
Example: "independent directors requirement" = part of П13.
→ Assign the existing parameter ID. Explain the mapping.

CATEGORY B — "Candidate for new": a genuinely new parameter, 
not covered by П01–П35. 
Example: "electronic settlement eligibility", "free transferability".
→ Assign temporary ID (CANDIDATE_01, CANDIDATE_02, ...). 
  Provide: name, description, in which lifecycle phases found, 
  in how many groups encountered.
→ Include in 3P prompts as CANDIDATE_XX (do not lose the data).

CATEGORY C — "Not a parameter": a procedural, architectural, 
or institutional element mistakenly extracted as a parameter.
Example: "two-gate admission model" = Г04 (admission architecture).
Example: "FCA supervisory powers" = institutional context.
→ Exclude from further processing. Log with reason.
```

**В. Критерии необходимости доразведки** (из рекомендаций разработчика ядра):

```
A parameter needs a 3P drill-down query if the Pass 1 description 
contains ANY of:

1. Reference to an external document without disclosing its content
   Example: "calculated per DDES methodology", 
   "as defined in SFO Schedule 1"

2. Ambiguity in exclusions
   Example: "holdings above certain thresholds are excluded" 
   — which thresholds exactly?

3. Mention of multiple alternative methodologies without detail
   Example: "may use either the profit test or the market cap test" 
   — what are the specific conditions of each?

A parameter does NOT need drill-down if:
- It is binary (yes/no, exists/not exists) — nothing to clarify
- The Pass 1 description already contains exact thresholds, 
  calculation methodology, exclusions, and verification mechanism
- It was marked "not_found" or "not_applicable" in Pass 1
```

**Г. Список типичных связок параметров:**

```
Known parameter linkages — when drilling down on one parameter 
in a linkage, ALWAYS ask about interaction with the other:

- П04 (min share price) × П05 (min number of shares) 
  = implicit monetary threshold
- П20 (min denomination, bonds) → П32 (investor eligibility)
  high denomination = de facto professional only
- П01 (free float %) ↔ П03 (min market cap of free float)
  percentage and absolute value as alternatives
- П15 (market maker) → П04 (min shareholders)
  market maker presence may lower shareholder count threshold
- П08 (profit test) ↔ П09 (assets/equity test) ↔ П10 (revenue test)
  alternative eligibility paths — clarify conditions for each
```

**Д. Шаблон промпта для 3P:**

```
TEMPLATE for 3P drill-down query:

Parameter: [ID and name]
Venue: [venue name]
Jurisdiction: [jurisdiction]
Instrument class: [class]

What is already known from the overview research:
[paste Pass 1 description for this parameter]

What needs clarification:
[specific question — generated by LLM based on drill-down criteria]

If this parameter is part of a linkage with [linked parameter]:
Does the calculation of [this parameter] depend on or interact 
with [linked parameter]? How?

Preferred source type: exchange rulebook, regulator guidance, 
or official methodology document. Do NOT use secondary analytical 
sources.

Cite specific rule numbers for each finding.
```

### Сообщение 2 (user)

Подаются данные 3A+3B+3C по всем ячейкам группы (как в Pass 1). Задание:

```
Here are the L3 research results (3A, 3B, 3C) for the group:
[jurisdiction] / [market_type] / [instrument_class]

Step 1: Extract parameters and map to the dictionary (П01–П35).
Step 2: Classify any UNKNOWN parameters per the rules in system prompt 
        (Category A / B / C).
Step 3: For each parameter — answer the 6-question template:
        1. What is established
        2. How is it calculated
        3. Alternatives
        4. Variations
        5. Linkages
        6. Source

Include parameters from ALL lifecycle phases found in the data 
(admission from 3A, continuing obligations/delisting from 3B, 
monitoring from 3C).

Note which lifecycle phases are covered. If a query_type has 
validation_status=RED — note that this phase is NOT covered.
```

### Сообщение 3 (assistant)

LLM возвращает результат Pass 1 по группе:
- Список параметров с маппингом на словарь
- Классификация UNKNOWN (A/B/C по каждому)
- 6-вопросный шаблон по каждому параметру
- Отметки о покрытых/непокрытых фазах ЖЦ

### Сообщение 4 (user)

```
Now evaluate each parameter from your Pass 1 result:

1. Does it need a 3P drill-down? Apply the criteria from 
   the system prompt (reference to external doc without content, 
   ambiguity in exclusions, multiple methodologies without detail).

2. For parameters that need drill-down — generate a Parallel API 
   prompt using the template from the system prompt. Include:
   - What is already known (from your Pass 1 result)
   - What specifically needs clarification
   - If the parameter is part of a linkage — include the linkage question

3. For parameters that do NOT need drill-down — state "no drill-down 
   needed" with brief reason (e.g., "binary parameter", 
   "methodology already fully described").

4. Generate a dynamic JSON schema for the 3P query. Schema structure:
   array of parameter objects, one per parameter needing drill-down:

{
  "parameters": [
    {
      "parameter_id": "string — П01 or CANDIDATE_01",
      "parameter_name": "string",
      "lifecycle_phases": "string — in which phases found",
      "definition_and_value": { "description": "string", "source": "string" },
      "calculation_methodology": { "description": "string", "source": "string" },
      "exclusions_and_inclusions": { "description": "string", "source": "string" },
      "alternatives": { "description": "string", "source": "string" },
      "variations": { "description": "string", "source": "string" },
      "linked_requirements": { "description": "string", "source": "string" },
      "differences_across_phases": { "description": "string", "source": "string" }
    }
  ]
}

Only include parameters that need drill-down. If no parameters 
need drill-down for this group — state explicitly.
```

### Сообщение 5 (assistant)

LLM возвращает:
- По каждому параметру: drill-down needed (да/нет) с обоснованием
- Для параметров с drill-down: готовый промпт для Parallel API
- Динамическая JSON schema для 3P
- Если drill-down не нужен ни по одному параметру — явное указание «3P not required for this group»

**Сохранить:** промпт и schema — в /prompts/ для воспроизводимости.

## 3. Запуск 3P через Parallel API

### Что запускается

Для каждой группы, где LLM определил необходимость доразведки — один запрос в Parallel API.

**Процессор:** core (запрос сфокусированный, координаты известны из Pass 1).

**Input:** промпт из сообщения 5.  
**Schema:** динамическая JSON schema из сообщения 5.

### Чего НЕ запускать

- Группы, где LLM указал «3P not required» — пропустить.
- Параметры, помеченные как «not_found» или «not_applicable» — не включать в 3P. Доразведка предполагает, что параметр уже найден, но его конструкция недостаточно описана.
- Бинарные параметры (П31 и подобные) — не включать.

### Результат

`3P_raw.json` на группу. Сохраняется в ту же директорию, что и результаты L3.

## 4. Pass 2 — извлечение значений по ячейкам

### Отдельный LLM-вызов (не продолжение диалога)

К моменту Pass 2 между сообщением 5 и запуском Pass 2 произошёл внешний вызов Parallel API (3P). Диалоговую цепочку продолжать нецелесообразно — контекст уже большой. Pass 2 — отдельный LLM-вызов с полным набором входных данных.

### Вход

- Результат Pass 1 по группе (из сообщения 3 диалоговой цепочки)
- Результат 3P по группе (`3P_raw.json`) — если был запущен
- Данные 3A+3B+3C по конкретной ячейке (не по всей группе — по одной ячейке)
- Словарь параметров (П01–П35+)

### Задание

```
You are given:
1. Parameter framework for the group [group ID] — extracted in Pass 1
2. Drill-down results from targeted research (3P) — if available
3. Overview research data (3A+3B+3C) for a specific cell: 
   [venue] / [tier] / [instrument_class]

For each parameter in the framework:
- Extract the SPECIFIC VALUE for this cell (tier/category)
- If 3P provided additional detail on calculation methodology — 
  incorporate it
- If no data found for this cell — mark as "not_found" or 
  "not_applicable" with reason
- Note lifecycle phase (admission / continuing / suspension / delisting)

Output format: one JSON object per parameter with fields:
- parameter_id
- parameter_name  
- value (the specific threshold/criterion for this cell)
- calculation_methodology (if clarified by 3P)
- alternatives
- variations
- linkages (references to other parameter IDs)
- lifecycle_phase
- source (specific rule/chapter)
- drill_down_applied (true/false — was 3P data used)

Mark lifecycle phases NOT covered (if any query_type was RED 
in validation).
```

### Единица выполнения

Один LLM-вызов на **ячейку** (не на группу). Группа может содержать несколько ячеек (разные тиры одного venue × instrument_class). Pass 1 и 3P — общие для группы. Pass 2 — индивидуальный для ячейки.

### Результат

`pass2.json` на ячейку. Содержит массив parameter_value по данной ячейке.

## 5. UNKNOWN_PARAM: жизненный цикл

### На этапе Pass 1 (в диалоговой цепочке)

LLM классифицирует каждый UNKNOWN:
- **Category A** (маппится на существующий) → получает ID из словаря, включается в 3P
- **Category B** (кандидат на новый) → получает CANDIDATE_XX, включается в 3P, логируется
- **Category C** (не параметр) → исключается, логируется с причиной

### На этапе 3P

CANDIDATE_XX обрабатываются наравне с параметрами словаря — по ним тоже может быть доразведка.

### На этапе Pass 2

CANDIDATE_XX извлекаются по ячейкам наравне с остальными.

### Периодическая ревизия (вне пайплайна)

После накопления данных по нескольким юрисдикциям — ревизия CANDIDATE_XX:
- Встречается в 3+ юрисдикциях → кандидат на формализацию (П36+)
- Встречается в 1–2 юрисдикциях → остаётся как CANDIDATE
- Ошибка классификации → реклассифицировать в A или C

Решение о формализации принимает разработчик концептуального ядра. Правило: обратная связь только на расширение — добавление новых параметров не инвалидирует ранее собранные данные.

---

## 6. Что делать с ячейками разных цветов

### GREEN (scope OK, completeness ≥ 0.5)

Полный цикл: Pass 1 → 3P → Pass 2.

### YELLOW (scope OK, completeness ≥ 0.5, source FAIL)

Полный цикл: Pass 1 → 3P → Pass 2. В итоговых данных ячейка помечена: «источники не верифицированы».

### RED (scope FAIL или completeness < 0.5)

Пайплайн по ячейке остановлен. Данные этой ячейки **не подаются** в Pass 1 / 3P / Pass 2. В итоговых данных: «данные не получены / недостаточны».

### Частичное покрытие (3A = GREEN, 3B = RED, 3C = GREEN)

Pass 1 получает данные только из GREEN/YELLOW query_types (3A + 3C в данном примере). В результате Pass 1 — явная пометка: «lifecycle phases covered: admission (3A), monitoring (3C); NOT covered: continuing obligations, suspension, delisting (3B = RED)». 3P и Pass 2 — только по покрытым фазам. В итоговых данных: ячейки матрицы по непокрытым фазам = «н/д».

## 7. Итоговая структура файлов

```
/level_3/{venue_key}/{cell_id}/
  3A_raw.json          — Parallel (обзор допуска)
  3B_raw.json          — Parallel (негативные аспекты)
  3C_raw.json          — Parallel (мониторинг)
  3A_cell.json         — постобработка (разнесение по ячейке)
  3B_cell.json
  3C_cell.json
  validation.json      — трёхцветная валидация

/level_3/{venue_key}/group_{group_id}/
  pass1.json           — результат Pass 1 (фреймворк параметров)
  pass1_unknowns.json  — классификация UNKNOWN_PARAM (A/B/C)
  3P_prompt.txt        — сгенерированный промпт для 3P
  3P_schema.json       — динамическая schema для 3P
  3P_raw.json          — результат Parallel (доразведка)

/level_3/{venue_key}/{cell_id}/
  pass2.json           — результат Pass 2 (значения по ячейке)
```

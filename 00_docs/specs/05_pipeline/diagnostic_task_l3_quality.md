# Задача: диагностика качества L3-результатов

**Дата:** 2026-03-10  
**От:** Архитектор пайплайна  
**Кому:** Tech Lead  
**Приоритет:** До запуска Task 005

---

## Контекст

Предоставленные примеры 3A/3B/3C результатов показывают обзорный уровень, недостаточный даже для обзорной фазы. Перед диагностикой промптов и процессоров нужно исключить ошибки логики пайплайна.

---

## Шаг 1. Идентификация ячейки

Указать для предоставленных примеров:
- `cell_id`
- `venue` (какая площадка)
- `tier` (какой уровень, или flat)
- `instrument_class`
- `legacy` (true/false)
- `admission_path` (standard / trading_only)

**Подозрение:** ссылки на UKLR 22.2 и «equity shares (transition)» указывают на legacy/transition ячейку, а не на основную ESCC. Если это transition — 3A для неё запускаться не должен (transition закрыта для новых эмитентов).

---

## Шаг 2. Проверка промптов

Для ячейки из шага 1 — показать фактический промпт, который был отправлен в Parallel (из /prompts/). Проверить:

**2.1. Привязка к конкретной UKLR-категории.**
Содержит ли промпт явное указание, КАКАЯ категория UKLR исследуется (ESCC, CEF, Transition, Shell)? Или содержит только «equities on LSE Main Market»? Если второе — Parallel сам выбирает категорию и может притащить данные по transition вместо ESCC.

**2.2. Указание глав rulebook.**
Содержит ли промпт ссылки на конкретные главы (UKLR 3, UKLR 5, UKLR 6 для ESCC; UKLR 22 для transition)? Если `rulebook_chapters` в venue_card пустой — промпт сформирован без ориентиров.

**2.3. Определение scope для split-архитектуры (Г04).**
Для UK (Г04 = split): содержит ли промпт явное указание, что нужны ОБА набора требований — FCA Official List (UKLR) И LSE Admission to Trading (ADS)? Или Parallel сам решает, где искать?

**2.4. Инструкция по глубине.**
Содержит ли промпт блок «For each requirement: what established, how calculated, alternatives, variations, links»? Или только «research the requirements»?

---

## Шаг 3. Проверка schema descriptions

Показать фактическую JSON schema, отправленную в Parallel для 3A. Проверить:

**3.1. Описания полей.**
Поле `instrument_requirements.description` — что написано в schema description? Если просто `"string"` без пояснения, что именно ожидается (пороги, расчёт, исключения) — Parallel не знает, какой глубины ответ нужен.

**3.2. Размер schema.**
Какой размер schema в символах? Был ли обрезан/упрощён для укладки в лимит 15 000 символов input?

---

## Шаг 4. Сравнение с нормальной ячейкой

Взять результат 3A по ячейке, которая точно не legacy и не transition (например, HKEX Main Board equities). Сравнить глубину. Если HKEX результат тоже поверхностный — проблема в промптах/schema. Если HKEX нормальный, а LSE поверхностный — проблема в идентификации ячейки или привязке к UKLR-категории.

---

## Шаг 5. Выводы

По результатам шагов 1–4 определить корневую причину:

| Причина | Признак | Действие |
|---------|---------|----------|
| 3A запущен по legacy-ячейке | cell = transition, legacy=true | Не перезапускать 3A, запустить 3B+3C |
| Промпт не привязан к UKLR-категории | Нет упоминания ESCC / UKLR 6 | Исправить генерацию промптов |
| Промпт без глав rulebook | `rulebook_chapters` пустой | Заполнить вручную для пилота |
| Schema descriptions пустые | Поля без пояснений | Добавить описания |
| Промпт без инструкции по глубине | Нет блока «for each requirement...» | Добавить блок |
| Core недостаточен | Все промпты корректны, но результат тонкий | Перезапустить на pro (но проверять в последнюю очередь) |

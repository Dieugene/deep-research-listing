# Пайплайн исследования: допуск и листинг ценных бумаг

## Итоговый обзор

**Дата:** 2026-03-11  
**Статус:** Пилот завершён (UK + Гонконг). Готов к масштабированию на 47 юрисдикций.

---

## 1. Цель и масштаб

Банк России проводит сравнительное исследование подходов к регулированию листинга ценных бумаг. Исследование охватывает 47 юрисдикций, ~120 торговых площадок (venue), 4 класса инструментов (акции, облигации, фонды, депозитарные расписки).

Данные собираются через Parallel Task API (deep research) по многоуровневому пайплайну с LLM-постобработкой на каждом уровне.

**Зависимости:**
- Концептуальное ядро v0 + патчи (словарь параметров, venue/tier/segment, ATT-only, модификаторы)
- Набор институциональных факторов (12 факторов Ф1–Ф12)
- Словарь параметров (П01–П35+, расширяемый)
- Спецификация информационной архитектуры + патчи
- Prompt-ready определения понятий от разработчика ядра

## 2. Архитектура

### 2.1. Иерархия объектов

Трёхуровневая (по патчу `pipeline_patch_venue_tier_segment.md`):

- **Operator (Б02):** институт, управляющий площадками. London Stock Exchange Group, HKEX.
- **Venue (А02):** площадка с собственной регуляторной рамкой и rulebook. LSE Main Market и AIM — разные venue одного оператора.
- **Tier (А05) / Segment (А04) / Modifier:** внутренняя структура venue. Тир — иерархия строгости. Сегмент — тематическая надстройка. Модификатор — изменение режима для типа эмитента (SPAC, WVR, biotech), не порождает отдельную ячейку.

Тест venue vs tier: есть ли собственный rulebook? Если да — venue. Тест tier vs segment: иерархия строгости или ортогональная надстройка? Тест segment vs modifier: собственное «место» на площадке или условия к типу эмитента?

Подробности: `pipeline_patch_venue_tier_segment.md`, `patch_systemic_classification_fix.md`.

### 2.2. Уровни пайплайна

```
Предварительный этап → Уровень 1 (юрисдикция) → Уровень 2 (venue) →
→ Уровень 3 (ячейка) → Уровень 4 (регуляторные цели)
```

### 2.3. Роли LLM

- **Постобработка** на каждом уровне: структурирование, формирование карточек, перевод на русский.
- **Формирование промптов** уровня 3: алгоритмическое (из блоков с подстановками), не через LLM. Определения понятий, условные блоки, переменные из карточек предыдущих уровней.
- **Диалоговая цепочка** для Phase 2: Pass 1 + классификация UNKNOWN + генерация промптов 3P — в одном диалоге на группу, с сохранением контекста.
- **Извлечение значений** (Pass 2): отдельный вызов на ячейку с полным набором входных данных.

### 2.4. Валидация

Трёхцветная система (по `spec_phase2_3p_pass2.md`, раздел 6):

- **GREEN:** scope OK + completeness ≥ 0.5. Пайплайн продолжается.
- **YELLOW:** scope OK + completeness ≥ 0.5 + source FAIL. Пайплайн продолжается, данные помечены «источники не верифицированы».
- **RED:** scope FAIL или completeness < 0.5. Пайплайн по ячейке останавливается. Данные помечены «н/д».

Source check — информационный, не блокирующий.

### 2.5. Обратная связь

**Только на расширение.** Добавление параметра (П36+), понятия, фактора — допускается. Ранее собранные данные остаются валидными. Переопределение существующих элементов — не допускается.

## 3. Предварительный этап

### Назначение
Сбор количественных институциональных факторов по всем 47 юрисдикциям из публичных датасетов.

### Реализация
Ручная загрузка с сайтов (World Bank DataBank, WFE, IOSCO, LLSV, CIA Factbook). Не через Parallel — данные требуют ручного скачивания.

### Факторы
Ф1 (правовая семья), Ф2 (ASDI — статутарная защита инвесторов), Ф4–Ф6 (WGI: качество регулирования, верховенство права, политическая стабильность), Ф7 (капитализация/ВВП), Ф10 (конкурентная структура площадок), Ф11 (тип регулятора).

### Зависимость
Не блокирует остальные уровни. Может выполняться параллельно или после основного сбора данных. Нужен до загрузки в PostgreSQL и до кластеризации.

## 4. Уровень 1. Юрисдикция

### Назначение
Архитектура допуска, маппинг архитектурных понятий ядра, качественные институциональные факторы, ландшафтный обзор площадок.

### Три запроса (параллельно внутри юрисдикции)

**1A. Архитектура допуска + маппинг понятий.**  
Deep Research, text, pro. Маппируются 5–7 архитектурных понятий: разделение листинга/допуска (Г02/Г03/Г04), листинговый орган (Б03), регулятор (Б04), типы рынков (А03), сегментация (А04/А05), разделение эмитент/инструмент (В04), вторичный допуск (Г06).

Для EU-юрисдикций — подставляется выжимка из кешированного результата по наднациональной рамке EU.

**1B. Институциональные факторы (качественные).**  
Deep Research, JSON schema, core. Факторы Ф3 (private enforcement), Ф8 (концентрация владения), Ф9 (инвесторская база), Ф12 (роль биржи как СРО). Плюс верификация предзагруженных данных.

**1C. Ландшафтный обзор площадок.**  
Deep Research, JSON schema, core. Перечень всех venue юрисдикции с типом рынка, оператором, тирами, сегментами, классами инструментов.

Промпт 1C содержит определения venue/tier/segment/modifier из ядра (по `pipeline_patch_venue_tier_segment.md`). Schema включает уровень operator → venues.

### LLM-постобработка
Карточка юрисдикции (jurisdiction_card.json). Перевод. Определение перечня venue для уровня 2. Если обнаружена неизвестная наднациональная рамка — пометка для динамического запроса.

### Наднациональные рамки
EU исследуется один раз заранее (ultra), результат сохраняется в /supranational/. Прочие рамки — при обнаружении на уровне 1: динамический запрос, результат сохраняется, при повторных упоминаниях — ссылка.

Определение наднациональной рамки: наднациональное законодательство, устанавливающее обязательные минимальные стандарты для допуска/листинга. Stock Connect, двусторонние меморандумы — не являются наднациональными рамками (по `pipeline_patch_pilot_review.md`, п. 2).

Подробности: `pipeline_v0_2.md`, разделы 3–4.

## 5. Уровень 2. Venue (площадка)

### Назначение
Детальная структура venue: тиры, сегменты, модификаторы, классы инструментов, специальные режимы. Результат определяет перечень ячеек уровня 3.

### Единица запроса
**Одна venue** (не оператор). Для оператора с несколькими venue (LSE: Main Market + AIM) — отдельные запросы.

### Запрос 2A
Deep Research, auto output, core. Промпт формируется LLM на языке площадки (подстановка из jurisdiction_card).

Промпт содержит два раздельных вопроса (по `patch_systemic_classification_fix.md`):
- Вопрос A (структура): тиры и сегменты.
- Вопрос B (инструменты): какие классы инструментов допускаются, по каким главам rulebook.

Критическое правило в промпте: «Instrument-class chapters are NOT tiers and NOT segments.»

Дополнительные вопросы: legacy-категории (закрытые для новых эмитентов), ATT-only путь (если Г04 = split), вторичный допуск.

### LLM-постобработка
Карточка площадки (venue_card.json). Генерация перечня ячеек (cells_list.json). Формирование промптов уровня 3 (алгоритмическое, из блоков с подстановками). Проверка классификации: venue vs tier, tier vs segment, segment vs modifier (тесты из `pipeline_patch_venue_tier_segment.md`).

Поле `issuer_eligibility` в venue_card ограничено архитектурным фактом: есть ли раздельная eligibility (да/нет), кто проводит, правовое основание. Конкретные требования — на уровне 3 (по `pipeline_patch_pilot_review.md`, п. 3).

Подробности: `pipeline_v0_2.md`, раздел 5; `patch_systemic_classification_fix.md`; `pipeline_patch_venue_tier_segment.md`.

## 6. Уровень 3. Ячейка

### Назначение
Основной объём исследования. Сбор фактических данных по правилам допуска, поддержания, исключения, мониторинга. Затем — извлечение и детализация параметров.

### 6.1. Единица запроса L3

**Venue × instrument_class** (не venue × tier × category × instrument_class). Все тиры/категории одного класса инструментов на venue — в одном запросе. Parallel на pro видит весь rulebook в контексте. Разнесение по ячейкам — при LLM-постобработке.

Переход на укрупнённые запросы обоснован: при узких запросах Parallel систематически путал категории (данные по Transition вместо ESCC на LSE). Подробности: `pipeline_patch_variant_b.md`, раздел 1.

### 6.2. Три обзорных запроса (Фаза 1, параллельно)

**L3-A: первичный допуск.** Требования, процедуры, раскрытие, спецрежимы. Pro.

**L3-B: негативные аспекты.** Поддержание обязательств, приостановка, исключение/делистинг. Pro. Отдельный запрос, потому что эти аспекты документированы скудно — при объединении с допуском Parallel перекашивает результат.

**L3-C: мониторинг и enforcement.** Надзор, санкции, дисциплинарные процедуры. Pro.

### 6.3. JSON schema

Компактная, на основе массива `tiers[]`. Структура тира определена один раз, Parallel заполняет столько элементов, сколько тиров/категорий найдёт. Размер schema не зависит от числа тиров.

Каждое поле description содержит детальную инструкцию: что описывать, с какой глубиной. Результаты должны быть максимально подробными (пороги, формулы, исключения, альтернативы, связки) — из них далее извлекаются параметры.

Подробности и полные schema: `pipeline_patch_variant_b.md`, раздел 3.

### 6.4. Формирование промптов

Алгоритмическое, из 9 блоков с подстановками и условными блоками:

1. Контекст venue (из venue_card)
2. Определения понятий (константа из ядра)
3. Задание поиска (шаблон + подстановка instrument_class, venue)
4. Условный: split-архитектура (если Г04 = split)
5. Условный: наднациональная рамка (если EU)
6. Инструкция по детальности (константа)
7. Перечень тиров для структурирования (из venue_card)
8. Условный: legacy-категории (если есть)
9. Закрывающая инструкция (включать всё найденное, цитировать правила)

Fallback при превышении лимита 15 000 символов: разбить scope по классам инструментов.

Подробности: `pipeline_patch_variant_b.md`, раздел 4.

### 6.5. LLM-постобработка обзоров

Разнесение массива `tiers[]` по ячейкам. Перевод на русский. Валидация (трёхцветная).

Legacy-ячейки (transition, закрытые для новых эмитентов): получают только L3-B + L3-C, без L3-A.

ATT-only ячейки (admission_path: "trading_only"): промпты ссылаются на Admission and Disclosure Standards, не на UK Listing Rules.

### 6.6. Phase 2: извлечение и детализация параметров

Выполняется как диалоговая LLM-цепочка (один диалог на группу ячеек).

**Группировка:** jurisdiction × market_type × instrument_class × admission_path_type.

**Диалог (5 сообщений):**

Сообщение 1 (system): словарь параметров, правила классификации UNKNOWN_PARAM (Category A — маппится на существующий / B — кандидат на новый / C — не параметр), критерии необходимости доразведки, список связок, шаблон промпта 3P.

Сообщение 2 (user): данные 3A+3B+3C по группе. Задание: извлечь параметры, смэппить, классифицировать UNKNOWN.

Сообщение 3 (assistant): результат Pass 1 (фреймворк параметров, маппинг, классификация).

Сообщение 4 (user): оценить необходимость доразведки по каждому параметру, сформировать промпты 3P для тех, где нужна.

Сообщение 5 (assistant): промпты 3P + динамическая schema.

Подробности: `spec_phase2_3p_pass2.md`, раздел 2.

### 6.7. Запрос 3P (доразведка параметров)

Parallel API, core. Запускается только по параметрам, требующим доразведки (три критерия: ссылка на внешний документ без раскрытия, неоднозначность в исключениях, множественные методики без детализации).

Динамическая JSON schema: массив объектов, по одному на параметр. Каждый объект: definition_and_value, calculation_methodology, exclusions_and_inclusions, alternatives, variations, linked_requirements, differences_across_phases.

При доразведке параметра из связки — обязательный вопрос о взаимодействии со связанным параметром.

CANDIDATE_XX (параметры вне словаря, Category B) включаются в 3P наравне с основными — чтобы данные не терялись.

Подробности: `spec_phase2_3p_pass2.md`, раздел 3; `3P_recommendations.md`.

### 6.8. Pass 2 (извлечение значений по ячейкам)

Отдельный LLM-вызов на ячейку (не продолжение диалога). Вход: Pass 1 + 3P + данные 3A/3B/3C по конкретной ячейке. Выход: pass2.json — массив parameter_value по ячейке.

При частичном покрытии (например, 3B = RED): Pass 2 работает только по GREEN/YELLOW query_types. Непокрытые фазы жизненного цикла помечены явно.

Подробности: `spec_phase2_3p_pass2.md`, раздел 4.

### 6.9. UNKNOWN_PARAM: жизненный цикл

- Pass 1: тройная классификация (A/B/C)
- 3P: Category B (кандидаты) включаются как CANDIDATE_XX
- Pass 2: извлекаются наравне с остальными
- Периодическая ревизия (после 10+ юрисдикций): кандидаты, встречающиеся в 3+ юрисдикциях → формализация (П36+). Решение — разработчик ядра.

Подробности: `spec_phase2_3p_pass2.md`, раздел 5.

## 7. Уровень 4. Регуляторные цели и обоснования

### Назначение
Сбор данных о регуляторных проблемах, противоречиях и обоснованиях, связанных с правилами допуска/листинга. Последний разведочный этап пайплайна.

### Единица запроса
Юрисдикция. Deep Research, text, pro.

### Четыре блока поиска
A. Регуляторные проблемы — какие обсуждались, кем, когда.
B. Противоречия между целями — какие цели конфликтовали, как разрешались.
C. Параметры как инструменты — какие параметры обсуждались как средства решения проблем.
D. Реформы — что менялось, какой драйвер, когда.

Промпт не содержит конкретных параметров из Pass 2. Parallel сам определяет, какие параметры обсуждались в регуляторном контексте.

Датировка — по каждой находке (год или период). Регуляторные цели меняются во времени.

### Постобработка
Структурирование в level4.json: массивы problems, contradictions, parameters_as_tools, reforms. Перевод на русский.

Связка с регуляторными целями РФ (Ц1–Ц5, ПА1–ПА5, ПБ1–ПБ10, К1–К4) — отдельный аналитический этап, не часть данного пайплайна.

Подробности: `spec_level4_regulatory_objectives.md`.

## 8. После уровня 4

### Перевод
LLM-батч по всем текстовым полям, которые ещё на английском. Source (названия законов, глав) не переводится.

### Viewer
Отображение всех уровней: карточки юрисдикций, карточки площадок, таблицы параметров по ячейкам (из Pass 2), блок регуляторных целей (уровень 4). Цветовая индикация validation_status.

Подробности: `spec_post_pass2_viewer.md`.

### Загрузка в PostgreSQL
После стабилизации формата данных. Схема БД — из спецификации информационной архитектуры (`spec_info_architecture.md` + патчи).

### Масштабирование
Та же последовательность шагов, больше объектов. Уровни 1–2 — параллельно по юрисдикциям/venue. Уровень 3 — максимальный параллелизм (venue × instrument_class независимы).

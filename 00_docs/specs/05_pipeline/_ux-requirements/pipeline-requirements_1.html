Запросы к пайплайну: постобработка для интерфейса

UX-дизайнер → Tech Lead / Пайплайн Март 2026

Документ содержит перечень полей и структур данных, которые нужны для реализации интерфейса согласно прототипам, но в текущих данных отсутствуют или структурированы иначе. Поскольку пайплайн запускается на переструктурирование, просим заложить эти элементы в постобработку. Каждый пункт содержит: что нужно, зачем, желаемый формат.

Блок 1 — Система источников

И-1 Классификация источника по типу документа все уровни Критично

Зачем: при 38–94 источниках на юрисдикцию список без фильтрации неудобен. Тип документа — основной способ навигации: аналитик хочет видеть только законодательные акты или только правила регулятора.

Что нужно: добавить поле type к каждому объекту источника во всех уровнях (L1, L2, L3, L4).

// Предлагаемые значения
type: "legislation"     // законы, директивы, регламенты
type: "rulebook"        // правила регуляторов и бирж
type: "government"      // правительственные документы, позиции
type: "consultation"    // консультативные документы, отзывы
type: "research"        // академические и аналитические работы
type: "other"           // прочее

Можно автоматически по домену (fca.org.uk → rulebook, legislation.gov.uk → legislation и т.д.) и уточнять LLM там где домен неоднозначен.

И-2 Привязка источников к блокам карточки юрисдикции jurisdiction_card.json Высокий

Зачем: сейчас L1-источники — объединённый пул без атрибуции по блоку. По прототипу каждый блок («Архитектура допуска», «Регулятор», «Примечания») должен иметь свой список источников с кнопкой «N источников» в шапке. Без атрибуции это невозможно реализовать честно.

Что нужно: при слиянии источников из raw-файлов сохранять признак происхождения:

{
  "url": "https://...",
  "title": "...",
  "type": "rulebook",
  "block": "architecture"  // "architecture" | "regulator" | "notes" | "general"
}

Источники из 1A_architecture → block: "architecture", из 1B_institutional → block: "regulator". Источники, не привязанные к конкретному блоку → block: "general" (попадут во вкладку «Источники» без привязки).

И-3 Привязка источников к отдельным записям регуляторного анализа level4.json Высокий

Зачем: сейчас один пул источников на весь L4-блок. По прототипу каждая запись (проблема, реформа, противоречие) в drawer должна показывать свои источники — именно те, которые обосновывают это конкретное утверждение.

Что нужно: добавить поле sources к каждой записи внутри Level4:

{
  "id": "prob-001",
  "type": "problem",
  "text_ru": "...",
  "sources": [           // источники именно этой записи
    { "url": "...", "title": "...", "type": "legislation" }
  ]
}

LLM при синтезе записи обычно опирается на конкретные документы — их можно извлечь из контекста генерации или попросить LLM явно указать при постобработке.

И-4 Текстовая цитата (excerpt) из первоисточника все уровни Средний

Зачем: регуляторный аналитик хочет видеть не только ссылку, но и дословный фрагмент нормы или правила — это принципиально другой уровень верификации по сравнению с пересказом LLM. «В документе написано X» vs «документ говорит буквально следующее».

Что нужно: опциональное поле excerpt — дословная цитата из документа, обосновывающая конкретное утверждение:

{
  "url": "https://...",
  "title": "UKLR sourcebook",
  "type": "rulebook",
  "excerpt": "An applicant for admission of equity shares to the UKLR must have a minimum market capitalisation of £30 million..."  // опционально
}

Поле опциональное — заполнять только там где LLM может извлечь точный фрагмент с высокой уверенностью. Лучше пустое поле чем галлюцинированная цитата.

Блок 2 — Записи регуляторного анализа (Level4)

А-1 Короткий лейбл для отображения на таймлайне level4.json Критично

Зачем: таймлайн отображает горизонтальные отрезки с подписями. Подпись должна быть ≤30–35 символов — иначе текст обрезается и теряет смысл. Сейчас используется начало полного текста, что даёт бессмысленные обрывки («В 2013–2014 годах после громких пр…»).

Что нужно: поле label — короткое смысловое название записи на русском, 3–6 слов:

{
  "label": "Защита миноритариев ENRC/Bumi",  // ≤35 символов
  "text_ru": "В 2013–2014 годах после громких провалов..."
}

LLM-задача: по полному тексту записи сгенерировать лаконичный лейбл — существительное или именная группа, без даты (дата есть в поле start/end).

А-2 Русский текст для всех записей level4.json Критично

Зачем: часть записей Level4 существует только на английском (особенно у Германии). Интерфейс полностью на русском — английский текст в карточках выбивается и снижает читаемость.

Что нужно: гарантировать наличие text_ru для каждой записи. Где поле отсутствует — перевести при постобработке. Аналогично для полей resolution_ru (у противоречий), problem_addressed, calibration_debate, opposition — все должны быть на русском.

А-3 Локализованные значения поля articulated_by level4.json → problems Средний

Зачем: поле уже используется в интерфейсе (тег «Поставили проблему»), но значения на английском ("government", "academic"). В интерфейсе нужны русские лейблы — либо добавить в постобработку, либо хранить маппинг на фронтенде.

Что нужно: либо добавить поле articulated_by_ru: string[] с готовыми русскими лейблами, либо ограничить значения фиксированным словарём чтобы фронтенд мог делать маппинг сам:

// Допустимые значения (enum):
"government"         → "правительство"
"regulator"          → "регулятор"
"academic"           → "академическое сообщество"
"market_participants" → "участники рынка"
"exchange"           → "биржа"

Если пайплайн выдаёт произвольные строки — нужна нормализация к этому словарю при постобработке.

Блок 3 — Карточка юрисдикции

Ю-1 Короткое название органа листинга jurisdiction_card.json Высокий

Зачем: поле listing_authority содержит длинный описательный текст («Exchange management (Börsengeschäftsführung) for the Regulated Market, decided by…»). В регулятор-стрипе нужно краткое название — иначе текст обрезается или ломает layout.

Что нужно: добавить поле listing_authority_short — краткое название, 1–5 слов:

{
  "listing_authority": "Exchange management (Börsengeschäftsführung) for...",
  "listing_authority_short": "Börsengeschäftsführung"
}
Ю-2 Схожие юрисдикции (кластеризация) jurisdiction_card.json Высокий

Зачем: блок «Похожие юрисдикции» в прототипе — одна из ключевых аналитических функций продукта для выявления релевантных примеров при выборе режима листинга для РФ. Сейчас блок показывает «В разработке».

Что нужно: массив схожих юрисдикций с коэффициентом сходства по институциональным факторам (правовая семья, WGI, структура рынка):

{
  "similar_jurisdictions": [
    { "name_ru": "Гонконг", "iso_code": "hk", "similarity": 0.91 },
    { "name_ru": "Австралия", "iso_code": "au", "similarity": 0.87 }
  ]
}

Алгоритм кластеризации — на усмотрение пайплайна. Минимум: по правовой семье + market_type + ключевым WGI-показателям. Желательно: взвешенная метрика по всем институциональным факторам.

Ю-3 Метрики Всемирного банка (WGI/WDI) jurisdiction_card.json Средний

Зачем: блок институциональных метрик в прототипе показывает Rule of Law, Regulatory Quality, Government Effectiveness и Market Cap/GDP. Сейчас везде «—». Это важные характеристики для сравнительного анализа юрисдикций.

Что нужно: загрузить из публичных датасетов Всемирного банка (WGI и WDI CM.MKT.LCAP.GD.ZS) и добавить в структуру:

{
  "world_bank_metrics": {
    "rule_of_law": { "score": 1.74, "percentile": 92, "year": 2022 },
    "regulatory_quality": { "score": 1.68, "percentile": 90, "year": 2022 },
    "gov_effectiveness": { "score": 1.42, "percentile": 88, "year": 2022 },
    "market_cap_gdp": { "value": 96.4, "year": 2022 }
  }
}

Данные статичные (не меняются чаще раза в год) — можно подгрузить один раз при построении датасета.

Блок 4 — Список юрисдикций

С-1 Нормализованное значение legal_family jurisdiction_card.json / list Высокий

Зачем: поле приходит с разным регистром («Civil law» / «civil law» / «Common Law»). Это ломает фильтрацию и вызывает дублирование кнопок фильтра в UI. Хотя фронтенд может нормализовать сам, правильнее исправить в источнике.

Что нужно: зафиксированный enum строчными буквами: "common law" | "civil law" | "mixed". Никаких вариаций.

С-2 Поле market_type (DM/EM) для всех юрисдикций jurisdiction_card.json / list Средний

Зачем: фильтр DM/EM в списке юрисдикций работает только если поле есть у всех записей. Проверить что оно заполнено для всех 47 юрисдикций в периметре.

Что нужно: поле market_type со значением "DM" или "EM" у каждой юрисдикции. Классификация стандартная (MSCI или FTSE Russell).

Блок 5 — Карточка площадки

П-1 Маппинг field-ключей L3 на читаемые лейблы level_3 citations Высокий

Зачем: L3 citations содержат поле field — техническое имя раздела JSON-схемы ("admission_overview", "eligibility_requirements"). Это позволяет показывать источники конкретного параметра на карточке площадки. Но field-ключи не читаемы пользователем.

Что нужно: предоставить таблицу всех используемых field-ключей с русскими лейблами. Формат — отдельный словарный файл или поле в схеме:

{
  "admission_overview": "Архитектура допуска",
  "eligibility_requirements": "Требования к эмитенту",
  "free_float": "Минимальный free float",
  // ... все используемые ключи
}

Без этой таблицы per-parameter sources на карточке площадки реализовать невозможно.

П-2 Нормализованный тип площадки venue_card.json Средний

Зачем: у ряда площадок Германии тип отображается как "other" — технический fallback. В интерфейсе это ничего не говорит пользователю.

Что нужно: нормализованное поле venue_type с фиксированными значениями:

"regulated_market"  // Regulated Market (RM)
"mtf"                // Multilateral Trading Facility
"otf"                // Organised Trading Facility
"exchange_regulated" // биржевой рынок вне RM (Freiverkehr и т.п.)

Текущий "other" для немецких площадок (Freiverkehr) скорее всего должен быть "exchange_regulated".

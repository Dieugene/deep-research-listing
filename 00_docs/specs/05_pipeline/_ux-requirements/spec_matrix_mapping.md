# Спецификация: маппинг L3-результатов в матрицу жизненного цикла 4×5

**Дата:** 2026-03-16  
**От:** Архитектор пайплайна  
**Кому:** Tech Lead  
**Контекст:** L3-данные собраны в структуре 3A/3B/3C (по принципу «что хорошо ищется вместе»). Для отображения нужна структура 4×5 — фазы жизненного цикла × типы регулятивного содержания (по принципу «что логично читать вместе»).

---

## 1. Задача

Преобразовать данные из полей JSON-результатов 3A, 3B, 3C в ячейки матрицы 4×5 для отображения во Viewer. Маппинг преимущественно детерминированный (алгоритмический), LLM нужен только для пограничных случаев.

---

## 4. Пограничные случаи (требуют LLM)

Три типа полей не маппятся однозначно на одну ячейку матрицы. Для них — LLM-вызов.

### 4.1. Sanctions (Д04) — распределение по фазам

Санкции из 3C описаны единым блоком, без разбивки по фазам. Но некоторые санкции явно привязаны к конкретной фазе:

- «Compulsory delisting as ultimate sanction» → Г07.4 × Д04
- «Suspension of trading pending investigation» → Г07.3 × Д04
- «Fine for late filing of annual report» → Г07.2 × Д04

**Правило:** LLM читает текст поля sanctions и для каждой отдельной санкции определяет фазу. Если фаза не указана явно — по умолчанию Г07.2 × Д04.

**Промпт для LLM:**

```
The following sanctions/enforcement text describes measures 
applicable to listed issuers on [VENUE].

For each distinct sanction or enforcement measure mentioned, 
determine which lifecycle phase it primarily relates to:
- G07.2 (maintenance) — sanctions for ongoing compliance breaches
- G07.3 (suspension) — suspension of trading as a sanction 
  or during investigation
- G07.4 (removal) — compulsory delisting, cancellation 
  as ultimate sanction

If a sanction applies to multiple phases (e.g., fines apply 
to any breach) — assign to G07.2 as the default phase.

Return the text split into sections by phase, preserving 
the original wording.
```

### 4.2. Monitoring (Д03) — мониторинг при приостановке

Основная масса мониторинга — фаза Г07.2 (поддержание). Но если в тексте `monitoring_regime` явно упоминается мониторинг в период suspension (например, «the exchange monitors compliance during suspension period»), этот фрагмент маппится на Г07.3 × Д03.

**Правило:** по умолчанию весь monitoring → Г07.2 × Д03. LLM проверяет, есть ли явные упоминания мониторинга при приостановке. Если есть — выделяет фрагмент в Г07.3 × Д03. Если нет — всё остаётся в Г07.2 × Д03.

### 4.3. Additional_findings

Поле `additional_findings` в 3A, 3B, 3C содержит содержание, не покрытое основными полями. Фаза и тип содержания не предопределены.

**Правило:** LLM определяет для каждого фрагмента additional_findings пару (фаза, тип содержания). Если не удаётся определить — сохранять как метаданные ячейки уровня 3, не маппить в матрицу.

## 5. Реализация

### 5.1. Алгоритмический маппинг (основной объём)

Скрипт, который для каждой ячейки уровня 3 (venue × tier × instrument_class):

1. Читает 3A_cell.json, 3B_cell.json, 3C_cell.json.
2. По таблице из раздела 3 — распределяет каждое поле в ячейку матрицы 4×5.
3. Для ячеек матрицы, куда попадает несколько полей schema (Г07.1 × Д01 получает 6 полей из 3A; Г07.4 × Д02 получает 4 поля из 3B) — объединяет в единый текстовый блок с подзаголовками.
4. Source по каждому полю — переносится в ячейку матрицы.

### 5.2. LLM-маппинг (пограничные случаи)

Один LLM-вызов на ячейку уровня 3. На вход — только поля, требующие LLM-маппинга:
- `sanctions.*` из 3C (распределение по фазам)
- `monitoring_regime.*` из 3C (проверка на упоминание мониторинга при приостановке)
- `additional_findings` из 3A, 3B, 3C (определение фазы и типа)

На выход — те же тексты, но с разметкой: к какой ячейке матрицы относится каждый фрагмент.

### 5.3. Сборка

Результаты алгоритмического и LLM-маппинга объединяются в итоговый файл:

```json
{
  "cell_id": "string",
  "venue": "string",
  "tier": "string",
  "instrument_class": "string",
  "matrix": {
    "G07_1": {
      "D01_requirements": {
        "content": [
          {
            "subtitle": "string — подзаголовок (эмитент / инструмент / инфраструктура / ...)",
            "description": "string",
            "description_ru": "string",
            "source": "string",
            "origin_field": "string — из какого поля schema взято (для трассировки)"
          }
        ]
      },
      "D02_procedures": { "content": [...] },
      "D03_monitoring": null,
      "D04_sanctions": null,
      "D05_disclosure": { "content": [...] }
    },
    "G07_2": {
      "D01_requirements": { "content": [...] },
      "D02_procedures": { "content": [...] },
      "D03_monitoring": { "content": [...] },
      "D04_sanctions": { "content": [...] },
      "D05_disclosure": { "content": [...] }
    },
    "G07_3": {
      "D01_requirements": { "content": [...] },
      "D02_procedures": { "content": [...] },
      "D03_monitoring": { "content": [...] | null },
      "D04_sanctions": { "content": [...] | null },
```

### 5.4. Обработка пустых ячеек

| Состояние | Значение | Как определяется |
|-----------|----------|-----------------|
| Заполнена | Данные собраны | `content` непустой |
| Не получены (н/д) | Данные не найдены Parallel | Поле schema пустое или query_type = RED |
| Не применимо | Ячейка нерелевантна | Г07.1 × Д03 (мониторинг при допуске — обычно не существует); определяется алгоритмически по фиксированному списку |

Фиксированный список «не применимо» (по умолчанию):
- Г07.1 × Д03 (мониторинг при допуске)
- Г07.1 × Д04 (санкции при допуске)
- Г07.4 × Д03 (мониторинг при исключении)

Если Parallel вернул данные для этих ячеек — не отбрасывать, а сохранять (бывают исключения).

## 6. Отображение во Viewer

### Матрица 4×5 на экране ячейки

Таблица 4 строки × 5 столбцов. Каждая ячейка матрицы:
- Если заполнена — цветной фон (интенсивность пропорциональна объёму), кликабельна.
- Если «не получены» — серый, пометка «н/д».
- Если «не применимо» — штриховка.

Клик по ячейке матрицы → раскрытие содержания: список блоков с подзаголовками, описаниями и источниками.

### Связь с параметрами (Pass 2)

Данные Pass 2 (parameter_value) привязаны к конкретным ячейкам матрицы через поле `lifecycle_phase`. На экране ячейки матрицы — ссылка «Параметры» → список parameter_value, относящихся к данной фазе ЖЦ × типу содержания.

## 7. Порядок выполнения

```
1. Алгоритмический маппинг (скрипт):
   3A/3B/3C cell.json → matrix.json (основной объём)

2. LLM-маппинг (батч, один вызов на ячейку):
   sanctions, monitoring, additional_findings → разметка по фазам

3. Сборка:
   Объединение алгоритмического и LLM-маппинга → итоговый matrix.json

4. Подключение к Viewer:
   matrix.json → экран матрицы 4×5 по каждой ячейке уровня 3
```

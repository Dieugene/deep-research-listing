00 Контекст и приоритеты

При разработке UI-прототипов часть элементов была спроектирована в расчёте на структуру данных, которой в реальном пайплайне не существует. Сейчас планируется повторный прогон LLM-обработки — это возможность заложить в пайплайн извлечение именно тех полей и структур, которые нужны UI.

Требования ниже сгруппированы по приоритету:

  • Обязательно (must) — без этого UI работает неправильно или ключевые элементы не отображаются
  • Важно (should) — значительно улучшает качество отображения
  • Желательно (nice) — обогащает интерфейс, но некритично
Принцип: все поля, которые пайплайн не может достоверно извлечь, должны получать явное значение null или пустой массив — не отсутствовать совсем. Это позволяет UI отличить «данных нет» от «поле не запрашивалось».

01 R-01 — Разделение фаз: три файла вместо двух

R-01 Три отдельных файла фаз: admission / maintenance / delisting
Обязательно

Проблема. Текущая структура: 3A (допуск) + 3B (всё после допуска смешанно) + 3C (мониторинг/санкции как надзорная деятельность). UI требует три чётких фазы жизненного цикла эмитента: допуск, поддержание листинга, исключение из списка. Файл 3B содержит нераздельно смешанный контент, который невозможно разнести без нового прогона.

Требуемая структура на выходе. Три файла (или три ключа в едином JSON) на каждую ячейку:

Сейчас
3A_raw — admission
3B_raw — maintenance + suspension + delisting (смешанно)
3C_raw — enforcement/monitoring
Нужно
phase_admission — первичный допуск
phase_maintenance — поддержание листинга
phase_delisting — приостановка и исключение

Что должно быть в каждой фазе.

Файл / ключМетка в UIСодержание
phase_admission Допуск Требования к эмитенту и инструменту для первичного листинга, процедура подачи заявки, раскрытие при допуске (проспект), спонсор/агент, специальные режимы (DCSS и т.п.), ограничения lock-up при допуске
phase_maintenance Поддержание Постоянные обязательства эмитента, периодическая отчётность, текущее раскрытие (инсайдерская информация, MAR), существенные сделки и связанные стороны, корпоративное управление в процессе листинга
phase_delisting Исключение Основания для приостановки торгов, процедура добровольного исключения, принудительное исключение регулятором, санкционные меры, требования к акционерам при исключении (порог голосования и т.п.)

Указание для LLM. При обработке исходного текста классифицировать каждый извлечённый блок информации по принадлежности к фазе на основе смысла, а не расположения в исходном документе. Критерий разграничения maintenance/delisting: если блок описывает что происходит при нормальном продолжении листинга — maintenance; если описывает условия прекращения или нарушения — delisting.

02 R-02 — Маппинг параметров к секциям контента

R-02 Каждый параметр (П01–П41) привязан к конкретной секции, в которой он упоминается
Обязательно

Проблема. Сейчас параметры хранятся плоским списком на уровне ячейки с полем lifecycle_phase, но без привязки к секции. В результате UI вынужден дублировать полный список параметров под каждой секцией — что делает страницу нечитаемой при реальных данных (наблюдался баг B-NEW-1).

Требуемое поле. В объекте параметра добавить поле section_keys — массив ключей секций, в которых этот параметр релевантен:

{
  "parameter_id": "P01",
  "lifecycle_phase": "admission",
  "section_keys": ["instrument_requirements", "admission_overview"],
  // ... остальные поля без изменений
}

Логика маппинга. LLM при извлечении параметра должна определить, в контексте какой секции он встретился в исходном тексте, и записать ключ этой секции. Если параметр упоминается в нескольких секциях — все ключи в массив. Если принадлежность неоднозначна — null.

Зачем. Это позволяет UI показывать параметры локально — только под той секцией, к которой они относятся — вместо глобального повтора. Полоса «Параметры» в секции рендерится только из параметров с совпадающим section_key.

03 R-03 — Топ-параметры фазы для карточки режима

R-03 Краткий набор ключевых параметров для каждой фазы на уровне ячейки
Обязательно

Проблема. Карточки режимов на странице площадки (/venues/:venue_key) должны показывать содержательные параметры прямо в теле карточки — в трёх колонках Допуск / Поддержание / Исключение. Сейчас там всегда «Параметры не извлечены», потому что venue-страница получает только оглавление ячеек (cells[] без параметров), а загружать полный контент каждой ячейки при загрузке venue-страницы — слишком тяжело.

Решение. Добавить в объект ячейки в /api/venues/:venue_key новое поле phase_highlights — компактный срез по 3–5 самых значимых параметров на фазу:

{
  "cell_id": "GB_LSE_Main_Market_equity_shares_commercial_compa_equity",
  "validation_status": "green",
  // ... существующие поля ...
  "phase_highlights": {
    "admission": [
      { "param_id": "P01", "label": "Free float", "value_short": "≥ 10%" },
      { "param_id": "P02", "label": "Market cap", "value_short": "≥ £30 млн" },
      { "param_id": "P12", "label": "История", "value_short": "≥ 3 года" }
    ],
    "maintenance": [
      { "param_id": "P25", "label": "Отчётность", "value_short": "Годовая + полугодовая" },
      { "param_id": "P27", "label": "Инсайд. раскрытие", "value_short": "MAR — немедленно" }
    ],
    "delisting": [
      { "param_id": "P38", "label": "Добров. исключение", "value_short": "≥ 75% акционеров" }
    ]
  }
}

Требования к value_short. Максимум 40 символов. Это значение отображается прямо в пилюле на карточке — должно быть коротким и самодостаточным. LLM при генерации должна сжимать значение до сути: числовые пороги, ключевые ограничения, нормативные ссылки опустить.

Критерий отбора топ-параметров. Приоритет — количественные и структурные параметры (пороговые значения, типы процедур), а не описательные. Для admission: free float, market cap, история деятельности, тип процедуры. Для maintenance: периодичность отчётности, режим раскрытия. Для delisting: порог голосования, основания исключения.

04 R-04 — Агрегаты по инструменту для обзорной страницы

R-04 Сводные данные по инструменту: охват и частотные параметры
Важно

Проблема. Страница «По инструментам» (/instruments) должна показывать на карточках каждого инструмента: сколько юрисдикций и режимов его покрывают, и какие параметры наиболее часто встречаются. Сейчас этих агрегатов нет — карточки не загружаются вообще.

Требуемый эндпоинт или поле. Новый эндпоинт /api/instruments/summary или дополнение к существующему каталогу параметров. Структура:

[
  {
    "instrument_class": "equity",
    "label_ru": "Акции",
    "jurisdictions_count": 42,
    "regimes_count": 98,
    "top_params_admission": [
      { "param_id": "P01", "label": "Free float", "occurrence_count": 87 },
      { "param_id": "P02", "label": "Market cap", "occurrence_count": 74 },
      { "param_id": "P07", "label": "История", "occurrence_count": 61 }
    ],
    "top_params_maintenance": [ /* аналогично */ ],
    "top_params_delisting": [ /* аналогично */ ]
  },
  /* equity, bond, fund, depositary_receipt */
]

Как считать occurrence_count. Количество ячеек (cell_id) данного инструмента, в которых параметр имеет статус found. Данные уже есть в pass2_ru.json — это агрегация, не новое извлечение. Может быть вычислен на бэкенде без повторного прогона LLM.

05 R-05 — Нормализация поля source

R-05 Поле source — структурированный массив, не plain-text строка
Важно

Проблема. Сейчас source — строка, где несколько источников разделены ;. UI вынужден парсить строку, угадывать где URL а где нормативная ссылка, и не может корректно отображать развёрнутый список источников с кликабельными ссылками.

Требуемая структура. Заменить строку на массив объектов:

"sources": [
  {
    "label": "UKLR 5.5.2R",          // короткое человекочитаемое название
    "url": "https://handbook.fca.org.uk/...",  // null если нет URL
    "type": "regulation"           // regulation | guidance | academic | other
  },
  {
    "label": "LSE ADS Schedule 1",
    "url": "https://docs.londonstockexchange.com/...",
    "type": "regulation"
  }
]

Обратная совместимость. Если повторный прогон невозможен — бэкенд может нормализовать существующие строки в массив при отдаче через API (как слой адаптации), без пересчёта пайплайна. Это допустимое промежуточное решение, но целевое состояние — массив из LLM.

Для кнопки «N источников» в шапке секции. UI считает sources.length — это возможно только при массиве. При строке количество нельзя определить без парсинга.

06 R-06 — Флаг is_legacy для устаревающих режимов

R-06 Булево поле is_legacy на уровне ячейки
Желательно

Что это. Некоторые листинговые режимы являются переходными или устаревающими — например, «Equity Shares (Transition)» на LSE после реформы UKLR 2024. В прототипе для таких режимов предусмотрен визуальный маркер Устаревающий на карточке тира.

Требуемое поле. В объект ячейки добавить:

"is_legacy": true  // или false, по умолчанию false

Критерий для LLM. Режим считается legacy если: (а) в источниках явно указано что режим закрыт для новых участников, или (б) режим введён как временная переходная категория с указанием срока действия или условия прекращения.

07 Итоговая схема изменений

Сводка по всем требованиям — что меняется, где и с каким приоритетом:

IDПриоритетТип измененияЧто меняется
R-01 must Новый прогон LLM Разделить 3B на phase_maintenance + phase_delisting. Переименовать 3A → phase_admission, 3C остаётся как аспект матрицы, не фаза.
R-02 must Новый прогон LLM Добавить поле section_keys: [] в объект параметра — к каким секциям он относится.
R-03 must Новый прогон LLM или бэкенд-агрегация Добавить поле phase_highlights в cells[] на уровне venue API — 3–5 параметров на фазу с коротким значением.
R-04 should Бэкенд-агрегация (без LLM) Новый эндпоинт /api/instruments/summary — подсчёт охвата и частоты параметров по instrument_class. Вычисляется из существующих данных.
R-05 should Новый прогон LLM (или адаптер на бэкенде) Поле source (строка) → sources (массив объектов с label, url, type). Промежуточно — адаптер парсинга на бэкенде.
R-06 nice Новый прогон LLM Добавить булево поле is_legacy в объект ячейки.
R-04 и частично R-05 можно реализовать без нового прогона LLM — силами бэкенда на существующих данных. Рекомендуется сделать это в первую очередь, чтобы разблокировать страницу инструментов, пока готовится полный прогон.
Порядок прогона. R-01 (разделение фаз) является базовым — R-02 и R-03 зависят от правильной фазовой структуры. Рекомендуется запускать их в одном прогоне, а не последовательно, чтобы не тратить ресурсы дважды.

# Перечень доработок веб-интерфейса (v2)

**Дата:** 2026-03-12  
**Основание:** Осмотр прототипа + обратная связь заказчика.  
**Принцип:** Рекомендации касаются только отображения и предобработки при рендеринге. Изменения структуры данных в базе — за рамками этого документа.

---

## Приоритет 1. Главная страница — витрина

Главная страница — первое, что видит любой пользователь. Сейчас она не впечатляет. Нужно, чтобы за 5 секунд было понятно: за этим стоит серьёзное, масштабное исследование.

### 1.1. Название проекта

**Проблема:** «Листинг ЦБ» читается как «листинг ценных бумаг Центрального банка» (которых нет) или вообще непонятно.

**Что сделать:** Заменить на ясное название. Варианты:
- «Листинг: сравнительная база» (коротко, понятно)
- «Глобальный справочник листинговых режимов» (описательно)
- «Listing Research» (если допустим английский)

Решение — за заказчиком, но «Листинг ЦБ» нужно убрать.

---

### 1.2. Карта мира — доминирующий витринный элемент

**Проблема:** Карта есть, точки кликабельны и показывают название при hover — это хорошо. Но визуально карта не доминирует, она занимает правую половину экрана и выглядит как иллюстрация, а не как центральный элемент.

**Что сделать:**

a) **Карта — на весь первый экран.** Не половина, а полный фон витринного блока. Текст заголовка и метрики — поверх карты (с полупрозрачной подложкой или без, в зависимости от контраста).

b) **Перспектива.** Рассмотреть вариант с наклонной проекцией (не плоская карта Меркатора, а перспективный вид — например, d3-geo orthographic projection с наклоном ~30°, или globe). Это сразу создаёт ощущение «глобального охвата» и выглядит принципиально иначе, чем стандартная плоская карта. Если 3D-глобус слишком тяжёл — хотя бы наклонная ортографическая проекция с анимацией медленного вращения при загрузке (останавливается, когда пользователь наводит курсор).

c) **Hover — мини-карточка с полезными данными.** Не просто название страны, а: название юрисдикции (рус + англ), количество площадок, перечень площадок (названия), правовая семья. Оформление: всплывающая карточка с аккуратной типографикой, мягкая тень, появление с анимацией (fade + slight shift). Это должно выглядеть как элемент дорогого продукта, а не как tooltip по умолчанию.

d) **Визуальные эффекты на точках.** Мягкое свечение (glow) вокруг точек юрисдикций с данными. Пульсация (subtle pulse) при загрузке страницы. Тонкие линии-дуги между юрисдикциями, у которых есть общие характеристики (одна правовая семья, или один кластер — когда данные появятся). Это создаёт визуальную сеть, а не набор изолированных точек.

e) **Дифференциация точек.** Юрисдикции с данными — яркие, крупные точки. Юрисдикции без данных (но в периметре) — тусклые, контурные, меньшего размера. Это показывает и масштаб периметра (47), и текущий прогресс — без абстрактных метрик «заполненности».

---

### 1.3. Метрики — контекст, а не голые числа

**Проблема:** Числа 47, 65, ~1000, 2 — есть, анимация есть. Но «2 из 47 юрисдикций охвачено пилотом» акцентирует пустоту.

**Что сделать:**

a) Переформулировать метрики так, чтобы они показывали масштаб замысла, а не текущую пустоту:
- «47 юрисдикций в периметре исследования»
- «65 торговых площадок»
- «4 класса инструментов»
- «~1000 режимов допуска для анализа»

Прогресс пилота — не в метриках, а в блоке «Охват данных» ниже (он там уже есть и хорошо работает).

b) Под метриками — 2–3 компактных мини-визуализации: распределение юрисдикций по правовым семьям (stacked bar, данные уже есть в базе), распределение площадок по типам рынков (regulated market / MTF / OTF). Это показывает структуру данных, а не их объём.

---

### 1.4. Навигационные метки

**Проблема:** «Параметры» в меню воспринимается как «Настройки». «Справочник» ведёт на список юрисдикций — это один из трёх входов, а не единственный.

**Что сделать:**

a) Переименовать пункты меню:
- «Справочник» → оставить, но сделать выпадающим: «По юрисдикциям» / «По инструментам» / «По параметрам».
- «Параметры» → «Сравнение параметров» или «Каталог параметров» (чтобы не путать с настройками).

b) Добавить в навигацию (хотя бы как неактивные пункты с пометкой):  «Анализ» (будущий раздел для кластеров и проблем), «Ассистент» (будущий бот).

---

### 1.5. Четыре карточки режимов — доработка

**Проблема:** Карточки «Справочник / Сравнительный анализ / Проблемный анализ / Аналитический бот» — структурно верны. Но «в разработке» на двух из четырёх + отсутствие превью создаёт ощущение незавершённости.

**Что сделать:**

a) Для активных карточек: добавить мини-превью с реальными данными. Для «Справочника» — миниатюра таблицы юрисдикций. Для «Сравнительного анализа» (он же «Параметры» в текущей навигации) — миниатюра каталога параметров или примера сравнительной таблицы.

b) Для неактивных: вместо серого «В разработке» — краткое описание того, что здесь будет, плюс примерная дата (если известна). Неактивные карточки — не «пустые», а «ожидающие».

## Приоритет 2. Внутренние страницы — аналитическая ценность

### 2.1. Карточка юрисдикции: маппинг терминов — оформление

**Проблема:** Таблица маппинга терминов (UK, 20+ строк) визуально тяжёлая. Все строки одинаковые, нет группировки, нет акцентов.

**Что сделать:**

a) Группировать записи маппинга по типу: архитектурные понятия (листинг/допуск, регулятор), нормативные акты, сегменты площадок, прочие термины. Группировка — при отображении, не в данных.

b) По умолчанию — свёрнутый блок, показывающий первые 5–7 ключевых маппингов. Кнопка «показать все» для полного списка.

---

### 2.2. Карточка юрисдикции: «Регуляторный анализ»

**Проблема:** Блок «Регуляторный анализ» содержит секции «Проблемы (6), Противоречия (4), Параметры как инструменты (8), Реформы (8)» — свёрнутые. Структура отличается от спецификации, но может быть содержательнее.

**Что сделать:** Не менять структуру, она сложилась из реальных данных. Но уточнить оформление: при раскрытии секции — нумерованные элементы с кратким описанием. Если элементы привязаны к конкретным параметрам или ячейкам матрицы — добавить перекрёстные ссылки (клик → переход к соответствующему параметру или ячейке площадки).

---

### 2.3. Страница площадки: матрица ячеек

**Проблема:** Ячейки показаны как карточки, сгруппированные по классам инструментов. Буквы «Д П М #» — компактны, но не считываются как матрица 4×5.

**Что сделать:**

a) Для каждого класса инструментов (акции, облигации, фонды, ДР) — показать ячейки в табличном формате: строки — уровни листинга / категории (Equity Shares Commercial, Equity Shares Transition и т.д.), столбцы — фазы ЖЦ (Д=допуск, П=поддержание, М=мониторинг, И=исключение). Цвет ячейки: есть данные (насыщенный) / нет данных (бледный). Клик — раскрытие содержания.

b) Внутри раскрытой ячейки: секции по параметрам (если данные структурированы по параметрам) или текстовый блок + источники (если нет). Статус верификации (GREEN/YELLOW/RED) — на уровне ячейки.

---

### 2.4. Каталог параметров: группировка и именование

**Проблема:** Плоский список 42 параметров. Плюс дубли (П01 и P01) и ADDITIONAL_* — но это вопрос данных, а не интерфейса.

**Что сделать на уровне отображения (без изменения данных):**

a) Группировать параметры по категориям при рендеринге. Логика группировки: по префиксу ID (П01–П07 = количественные к инструменту, П08–П12 = к эмитенту, и т.д.) или по маппингу ID → категория в конфиге фронтенда.

b) Параметры с ID «ADDITIONAL_*» — визуально выделить как «Дополнительные / нераспределённые» (отдельная секция внизу, приглушённый стиль).

c) Если в базе есть дубли (П01 и P01), фронтенд может группировать их при отображении (показывать как один параметр с суммарной частотностью и пометкой «встречается с альтернативными ID»). Это предобработка при рендеринге, не изменение данных.

---

### 2.5. Статусы верификации — зафиксировать

**Проблема:** Статусы «Проверить источники» (YELLOW) и «Ненадёжно» (RED) уже реализованы, но не описаны в спецификации.

**Что сделать:** Зафиксировать как элемент спецификации (добавить п. 8.5):

| Статус | Цвет | Значение |
|--------|------|----------|
| Верифицировано | Зелёный | Источники подтверждены |
| Проверить источники | Оранжевый | Данные есть, но источники требуют проверки |
| Ненадёжно | Красный | Данные могут содержать ошибки |

Это полезное дополнение, его нужно сохранить и обеспечить единообразие по всем страницам.

## Приоритет 3. Качество исполнения

### 3.1. Типографика

**Проблема:** Системный шрифт без характера.

**Что сделать:** Подобрать пару шрифтов с кириллической поддержкой. Заголовки — шрифт с характером (Manrope, PT Sans Caption, Onest — есть кириллица). Основной текст — читаемый гротеск (PT Sans, IBM Plex Sans, Source Sans 3). Числа в таблицах — tabular figures. Зафиксировать как CSS-переменные.

---

### 3.2. Сравнительная таблица «от параметра» — группировка по типу конструкции

**Проблема:** Клик по параметру в каталоге (предположительно) показывает список ячеек. Но нет сравнительной таблицы с группировкой по типу конструкции параметра.

**Что сделать:** При отображении страницы параметра — группировать значения не по алфавиту юрисдикций, а по типу конструкции (процентный порог / денежный порог / скользящая шкала / качественный). Тип конструкции определяется при рендеринге на основе текста описания или предзаполненного поля (если оно есть в данных). Внутри группы — сортировка по числовому значению (если применимо).

---

### 3.3. Перекрёстные ссылки между разделами

**Проблема:** Навигация линейная: юрисдикция → площадка → ячейка. Нет горизонтальных связей (от параметра → к ячейкам в разных юрисдикциях; от регуляторного анализа → к конкретным параметрам).

**Что сделать:** При отображении параметра в ячейке — ссылка «Сравнить этот параметр по всем юрисдикциям» → переход на страницу параметра в каталоге. При отображении элемента регуляторного анализа — ссылки на связанные параметры/ячейки (если связь есть в данных).

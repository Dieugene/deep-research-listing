# Эскалация: система источников — расхождение спецификации и данных

**Кому:** UX-дизайнер
**От:** Tech Lead
**Дата:** март 2026
**Контекст:** Разработчик пайплайна восстановил структуру источников во всех файлах данных. Перед реализацией — сверка с оригинальными директивами UX. Обнаружены существенные расхождения.

---

## 1. Что предполагалось (оригинальные директивы)

### Из `listing-research-dev-spec.html` — раздел «Система источников»

**Ожидаемый формат данных:**
```json
{
  "id": "src-001",
  "label": "FCA UK Listing Rules (UKLR) sourcebook",
  "url": "https://www.fca.org.uk/...",
  "type": "rulebook",   // rulebook | legislation | consultation | report | other
  "year": 2024,
  "note": ""
}
```

**Архитектура отображения (три уровня):**
1. Сноска `[1]` в тексте блока — клик → прокрутка к списку
2. Кнопка «N источников» в шапке карточки-блока
3. Нумерованный список внизу блока

**Правило по количеству:**
| Кол-во | Поведение |
|--------|-----------|
| 1–5 | Сразу показать всё |
| 6–15 | Первые 5 + «показать ещё N» |
| 16+ | Кнопка → модал/drawer со скроллом, **поиском и фильтром по `type`** |

**Принцип:** источники — не сноски, а часть интерфейса. Каждый блок данных имеет свои источники.

> *Прямая инструкция из спека: «If the source structure in the database differs from the expected format — **escalate**».*

### Из `ui-tasks.html`, задача К-2

Места отображения источников:
- **Карточка юрисдикции** — кнопка «N источников» в шапке каждого блока («Архитектура допуска», «Регулятор», «Примечания») + нумерованный список внизу блока
- **Drawer регуляторного анализа** — список источников в конце каждой отдельной записи (проблемы / противоречия / параметры / реформы)
- **Карточка площадки** — источники при каждом параметре

## 2. Что есть в действительности

### Структура полученных данных

Все поля источников в восстановленном пайплайне имеют одинаковую структуру — массив объектов:

```json
[
  {
    "url": "https://www.fca.org.uk/publications/...",
    "title": "PS24/6: Primary Markets Effectiveness Review",
    "field": "content"
  }
]
```

**Присутствует:** `url`, `title` (может быть пустым), `field` (внутреннее имя поля JSON-схемы).
**Отсутствует:** `id`, `label`, `type` (rulebook/legislation/etc.), `year`, `note`.

### Размещение источников в данных

| Уровень | Файл | Поле | Гранулярность | Объём |
|---------|------|------|---------------|-------|
| L1 | `jurisdiction_card.json` | `sources` | На всю юрисдикцию | 38–94 источника |
| L2 | `venue_card.json` | `sources` | На площадку | 2–7 источников |
| L3 | `level_3/.../_raw.json` | `citations` | На ячейку (фильтр по `field`) | переменно |
| L4 | `level4.json` | `sources` | На весь блок регуляторного анализа | 23–41 источника |

**Объём по юрисдикциям (L1):**

| Юрисдикция | L1 sources | L4 sources |
|------------|-----------|-----------|
| Австралия | 94 | 34 |
| Великобритания | 57 | 41 |
| Германия | 78 | 33 |
| Гонконг | 38 | 23 |
| Сингапур | 55 | 36 |
| Франция | 62 | 36 |
| Россия | — | — |

## 3. Расхождения: спецификация vs реальность

### Р-1. Формат данных не совпадает со спецификацией

| Поле | Ожидалось | Есть |
|------|-----------|------|
| `id` | ✅ строка-идентификатор | ❌ отсутствует |
| `label` | ✅ отображаемое имя | ❌ только `title` (может быть пустым) |
| `type` | ✅ классификация (rulebook / legislation / consultation / report / other) | ❌ отсутствует |
| `year` | ✅ год документа | ❌ отсутствует |
| `note` | ✅ комментарий | ❌ отсутствует |
| `field` | ❌ не предполагалось | ✅ есть — имя поля JSON-схемы (технический атрибут) |

**Следствие:** фильтрация по типу документа в drawer 16+ — **невозможна** без добавления `type` в пайплайн.

### Р-2. Источники — документ-уровневые, не per-block

Оригинальный дизайн предполагал, что у каждого блока карточки («Архитектура допуска», «Регулятор», «Примечания») есть **свой** набор источников. Кнопка «N источников» в шапке блока — именно под это.

**Реальность:** L1-источники представляют собой объединённый пул из трёх raw-файлов (1A_architecture + 1B_institutional + 1C_venues) **с дедупликацией по URL**. Атрибуция по блоку утрачена при слиянии. Технического способа определить, «к какому блоку» относится конкретный источник — нет.

Исключение: поле `field` в L3-файлах (`citations`) содержит имя раздела JSON-схемы — это позволяет привязать источник к конкретному параметру на уровне ячейки (`admission_overview`, `eligibility_requirements` и т.д.). Но это технические имена схемы, не блоки UI.

### Р-3. L4-источники — на весь раздел, не на каждую запись

К-2 предполагал: «список источников в конце каждой отдельной записи» в drawer.
**Реальность:** один массив `sources` в корне `level4.json` — общий для всех проблем, противоречий, параметров и реформ. Атрибуции «этот источник — для этой реформы» нет.

Старое строковое поле `source: string` в отдельных записях Level4 — это артефакт прежнего формата (текстовая ссылка от LLM), не URL.

### Р-4. Масштаб в 10–20 раз превышает предположения прототипа

Dev-spec констатирует: «Прототипы показывают 2–4 источника на блок — в реальности может быть 10–20».
**Реальность превысила и этот ориентир:** UK — 57 L1-источников на карточку, DE — 78, AU — 94. При паттерне «кнопка «N источников» в шапке блока» и отсутствии per-block разбивки кнопка всегда ведёт к 38–94 источникам — фактически это всегда режим drawer 16+. При этом фильтр по `type` недоступен (данных нет).

## 4. Вопросы к UX-дизайнеру

В текущем состоянии данных нельзя реализовать оригинальный дизайн без одного из двух: либо дополнить данные, либо пересмотреть дизайн. Нужно решение по каждому пункту.

**В-1. Расположение источников в карточке юрисдикции**

Per-block атрибуция недоступна. Варианты:
- **А)** Одна секция «Источники» в конце вкладки «Юрисдикция» со всем пулом (38–94 ссылок) — проще, честнее отражает данные
- **Б)** Попросить пайплайн добавить `type` и/или block-attribution в источники — тогда per-block дизайн возможен, но это работа на стороне пайплайна

**В-2. Drawer регуляторного анализа**

Источников на запись нет. Варианты:
- **А)** Секция «Источники анализа» в конце вкладки «Регуляторный анализ» (23–41 ссылка) — сигнализирует «откуда взят весь анализ»
- **Б)** Не показывать источники в этом разделе — ждать per-item attribution от пайплайна

**В-3. Классификация источников (`type`)**

Поля `type` нет ни в одном файле. Варианты:
- **А)** Реализовать без фильтра по типу — просто список ссылок с `title` / hostname
- **Б)** Попросить пайплайн добавить `type` (можно автоматически по домену: `fca.org.uk` → legislation, `docs.londonstockexchange.com` → rulebook и т.д.)

**В-4. L3 citations на уровне параметров**

Эти источники фильтруются по `field` (имя раздела схемы) и потенциально позволяют показать «источник для этого параметра». Но `field` — технический ключ (`admission_overview`, `eligibility_requirements`), не читаемый пользователем заголовок. Нужно решение:
- **А)** Сопоставить `field`-ключи с читаемыми лейблами (таблица маппинга) — тогда per-parameter sources на карточке площадки возможны
- **Б)** Показывать только на уровне ячейки, без per-parameter разбивки

**В-5. Масштаб и режим работы с источниками**

78–94 источника на юрисдикцию — это материал для самостоятельного исследования первичных источников, а не «сноски для верификации». Возможно, правильный ответ — **отдельная вкладка «Источники»** (или «Библиография») вместо встроенных кнопок в блоки. Это принципиально иной UX-паттерн, и он не конфликтует с существующей архитектурой вкладок.

## 5. Что можно реализовать прямо сейчас (не требует решений)

Следующие изменения не зависят от решений выше и могут быть реализованы немедленно:

1. **Бэкенд**: пробросить `sources` из `jurisdiction_card.json`, `venue_card.json`, `level4.json` через Pydantic-модели и репозитории
2. **Фронтенд**: добавить тип `SourceCitation`, обновить TypeScript-интерфейсы
3. **UI**: минимальная реализация — секция «Источники» в конце вкладки «Юрисдикция» со всем пулом (вариант А по В-1), аналогично для вкладки «Регуляторный анализ»

Эта реализация не предрешает финальный дизайн и может быть уточнена после получения директив.

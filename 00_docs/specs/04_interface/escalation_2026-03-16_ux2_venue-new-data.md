# Эскалация к UX-дизайнеру №2: новые данные на странице площадки

**Кому:** UX-дизайнер №2 (карточка площадки, детальный вид ячейки, страница инструментов)
**От:** UX-разработчик
**Дата:** 2026-03-16
**Контекст:** Пайплайн завершил обновление данных. Появились новые поля, часть из которых требует дизайн-решений перед реализацией. Также уточняем решение по фазам, принятое в предыдущей итерации.

## Вопрос 1 — Фазы: подтвердить итоговую структуру вкладок

**Предыстория:**
В предыдущей итерации вы приняли решение о Варианте Б: 2 вкладки («Допуск» / «После допуска»), т.к. пайплайн не разделял данные по поддержанию и исключению.

**Что изменилось:** Пайплайн завершил разделение фаз (R-01). Теперь в данных три отдельных фазы:
| Ключ в данных | Содержимое |
|---|---|
| `phase_admission` | Требования к допуску, процедура, проспект, спонсор |
| `phase_maintenance` | Постоянные обязательства, отчётность, раскрытие информации |
| `phase_delisting` | Приостановка торгов, добровольное и принудительное исключение, санкции |
| `enforcement` (3C) | Мониторинг/надзор — только в матрице инструментов, не фаза |

**Вопрос к дизайнеру:**
Подтвердите итоговую структуру вкладок в детальном виде ячейки:

- **А (рекомендую):** 3 вкладки: «Допуск» / «Поддержание» / «Исключение». Откатить Вариант Б, использовать полноценные фазы.
- **Б:** Сохранить 2 вкладки: «Допуск» / «После допуска» (не использовать разделение).
- **В:** Другое решение.

**Уточняющий вопрос (если выбран вариант А):** Что показывать, если для конкретного режима фаза `phase_delisting` не заполнена данными — скрывать вкладку или показывать пустое состояние?

## Вопрос 2 — section_keys: параметры под секциями или единая полоса?

**Что появилось в данных:**
Каждый параметр в `pass2_ru.json` теперь содержит массив `section_keys[]` — ключи секций, в которых этот параметр упоминается. Например:

```json
{
  "parameter_id": "P01",
  "lifecycle_phase": "admission",
  "section_keys": ["instrument_requirements", "admission_overview"],
  "value": "≥ 10%"
}
```

**Что это даёт:**
Параметры можно отображать локально — только под той секцией, к которой они относятся, а не единым списком в конце фазы.

**Текущее поведение:** Все параметры фазы — одна полоса под всеми секциями (исправленный B-NEW-1).

**Два возможных подхода:**

| | Вариант А: локальные параметры | Вариант Б: единая полоса (текущий) |
|---|---|---|
| Где параметры | Под каждой секцией (только релевантные) | Одна полоса в конце фазы |
| Плюс | Контекстно, читабельно | Проще, компактнее |
| Минус | Параметр может быть в нескольких секциях → дублирование | Нет привязки к контексту |

**Вопрос к дизайнеру:** Какой вариант реализовывать?

Если **Вариант А** — дополнительный вопрос: параметр с несколькими `section_keys` показывать во всех перечисленных секциях или только в первой?

## Вопрос 3 — venue_type: метка для нового значения

**Что изменилось:**
Поле `venue_type` нормализовано к четырём значениям. В данных появилось новое:

| Значение | Текущая метка | Пример площадок |
|---|---|---|
| `regulated_market` | Regulated Market | LSE Main Market |
| `mtf` | MTF | LSE AIM |
| `otf` | OTF | — |
| `exchange_regulated` | **нет метки** ← нужна | Frankfurter Wertpapierbörse Freiverkehr (Германия) |

**Вопрос к дизайнеру:**
Какую метку использовать для `exchange_regulated`?

- **А)** «Биржевой рынок» (общее описание)
- **Б)** «Нерегулируемый сегмент» (подчёркивает отличие от RM)
- **В)** «Exchange-Regulated» (оставить на английском, как MTF/OTF)
- **Г)** Другое.

**Контекст:** Метки MTF и OTF сейчас также на английском — если меняем стиль для exchange_regulated, возможно стоит привести все три к единому стандарту.

## Справочно: что уже работает без вопросов

- `venue_type` lowercase bug в бэкенде — исправляем в этом же спринте без вашего участия (добавляем ключи `mtf`, `otf` + `exchange_regulated` в словарь меток)
- `ParamPill` поля переименованы (`code` → `param_id`, `value` → `value_short`) — обновляем фронтенд, визуально ничего не меняется
- `legal_family` нормализован, фильтрация на странице инструментов — работает без изменений

01 Прототипы и их назначение

К этому ТЗ прилагаются два интерактивных HTML-прототипа. Прототипы демонстрируют организацию данных и логику взаимодействия, а не финальный визуальный стиль (CSS-токены из прототипов переносятся как есть, компоненты реализуются в соответствии с общими требованиями к дизайн-системе).

ФайлЧто покрывает
00_docs\specs\04_interface\_final_prototypes\venues\venue.html Страница торговой площадки: шапка площадки, мета-бар, описание, sticky-вкладки инструментов, карточки листинговых режимов (тиры/категории) с параметрами по фазам, детальный вид режима (вкладки Допуск / Поддержание / Исключение + матричный вид как альтернатива). Демонстрируется на двух примерах: LSE Main Market (с тирами) и HKEX GEM (плоская структура).
00_docs\specs\04_interface\_final_prototypes\instruments\instruments.html Страница «По инструментам»: sticky-карточки 4 инструментов (обзор + переключатель), split-layout с левой панелью фильтрации / выбора режимов и правой сравнительной таблицей, переключение фаз и параметров-столбцов.
Важно: данные в прототипах — тестовые заглушки. При реализации все значения берутся из API. Структура компонентов (иерархия, порядок элементов, логика переключения) воспроизводится точно; числовые значения и тексты — из реальных данных.

02 Маршрутизация (URL-схема)

В прототипах несколько логических экранов объединены в один HTML-файл для удобства демонстрации. В продакшене каждый экран должен иметь собственный URL — это необходимо для работы кнопок «назад/вперёд» браузера, для возможности поделиться ссылкой на конкретный режим и для SEO.

МаршрутЭкранФайл прототипа
/venues/:venue_key Страница площадки — шапка, описание, вкладки инструментов, карточки режимов venue.html
/venues/:venue_key/:cell_id Детальный вид листингового режима — вкладки Допуск/Поддержание/Исключение и матричный вид venue.html (переход по клику на карточку режима)
/instruments Страница «По инструментам» — сравнительный вид instruments.html

Сохранение состояния в URL

Следующие параметры состояния должны отражаться в URL, чтобы страница правильно открывалась по прямой ссылке:

  • На /venues/:venue_key — активная вкладка инструмента: ?tab=equity
  • На /venues/:venue_key/:cell_id — активная фаза: ?phase=admission, активный вид: ?view=tabs или ?view=matrix
  • На /instruments — активный инструмент и активная фаза: ?instr=equity&phase=admission. Выбранные режимы (чекбоксы) в URL не сохраняются — это сессионное состояние.
Внимание: sticky-полоса с карточками инструментов на странице площадки (/venues/:venue_key) — это переключатель вкладок, а не переход между URL. Смена вкладки инструмента обновляет только query-параметр ?tab=, не меняет venue_key.

03 Принципы соответствия данных и дизайна

Прототипы разработаны на основе анализа структуры API и тестовых данных, но не проверялись на полном реальном датасете. При реализации разработчик неизбежно столкнётся с расхождениями. Ниже — принципы принятия решений.

Иерархия ценностей при конфликте

При любом расхождении между прототипом и реальными данными руководствуйтесь следующей приоритизацией:

ПриоритетЧто сохранить любой ценой
1 — Обязательно must Логика «что пользователь видит прежде всего». Карточка режима показывает содержательные параметры (free float, market cap), а не технические индикаторы объёма данных. Источники — на каждый блок, не на страницу целиком. Три фазы жизненного цикла — первичная навигация в детальном виде.
2 — Сохранить should Параметровые пилюли в карточках режимов. Статусы верификации (green/yellow/red). Разделение «Допуск / Поддержание / Исключение». Split-layout с фиксированной левой панелью на странице инструментов.
3 — Желательно nice Точные наборы параметров по умолчанию. Конкретные значения счётчиков (сколько юрисдикций, режимов). Sticky-тени и анимации.

Конкретные ситуации — что делать

СитуацияРешение
У площадки нет тиров (flat structure) Показывать одну карточку режима без уровня тира. Логика прототипа HKEX GEM — референс.
Тиров больше, чем в прототипе (например, 10+) Список прокручивается вертикально внутри вкладки инструмента. Пагинация не нужна — все карточки отрисовываются, virtualisation по желанию.
Параметров в карточке режима нет или меньше 3 Показывать столько, сколько есть. Если параметров нет совсем — показывать плашку «Параметры не извлечены» вместо пустой колонки.
Параметров в карточке режима больше, чем в прототипе Показывать все доступные параметры, не обрезать. Колонки тела карточки растягиваются по контенту.
Для инструмента нет данных по одной из фаз Вкладка фазы показывается, но с состоянием «Данные в работе» (серый placeholder). Вкладку не скрывать — пользователь должен знать, что фаза существует.
В сравнительной таблице у режима нет значения по параметру Ячейка показывает «—» (тире), не пустую строку.
Структура sections[] в ячейке отличается от прототипа Каждая section рендерится как отдельный блок с заголовком section_label и телом text. Порядок — по порядку в API-ответе. Неизвестные section_key не игнорировать, показывать как обычный блок.
Поле listing_architecture = null Строку «Архитектура допуска» в мета-баре не показывать. Не показывать placeholder «нет данных».

04 Протокол эскалации при расхождениях

Если при реализации возникает ситуация, когда разработчик не понимает, как соотнести реальные данные с прототипом, и правило из раздела 03 не даёт однозначного ответа — необходима эскалация. Молча «как-то решить» нельзя.

Порядок эскалации
1.Зафиксировать проблему в отдельном файле. Формат: escalation_YYYY-MM-DD_тема.md. Пример: escalation_2026-03-20_venue-tiers.md
2.Структура файла: Раздел (какой экран/компонент затронут), Проблема (что конкретно не сходится — ссылка на поле API, описание расхождения), Варианты решения (минимум 2, с плюсами и минусами каждого), Предпочтительный вариант разработчика с обоснованием.
3.Уведомить руководителя проекта: тема письма/сообщения — «[ЭСКАЛАЦИЯ] Listing Research — тема». Приложить файл или указать путь к нему.
4.До получения ответа — заглушить проблемный блок состоянием «В разработке» и продолжить работу над остальными частями. Не блокировать весь релиз из-за одного нерешённого вопроса.
Недопустимо: молча убирать компоненты из UI, показывать данные в неструктурированном виде («сырой JSON»), или оставлять пустые блоки без состояния — только потому что данных нет или они не подходят по формату.

05 Система источников — обязательный подход

Прототипы демонстрируют 1–3 источника на блок — это заглушки. В реальных данных источников на блок может быть значительно больше (10–20+). Ниже — обязательный подход к отображению.

Трёхуровневая система

1
Суперскрипт в тексте обязательно
Цифра-ссылка 1 прямо в тексте секции. Привязана к конкретному утверждению. При клике — плавная прокрутка к соответствующей строке в блоке источников с кратковременной подсветкой (highlight + setTimeout 1.5s). Реализуется через section.source или parameter.source из API.
2
Блок источников секции — collapse/expand обязательно
Каждая секция контента имеет свой блок источников внизу. По умолчанию показываются первые 3 источника. Если источников больше — кнопка «Показать ещё N источников» раскрывает остальные прямо на месте (без модального окна, без перехода). Повторный клик сворачивает. Состояние expand/collapse — локальное для каждой секции независимо.
3
Кнопка «N источников» в шапке блока — для быстрого обзора желательно
В заголовке карточки секции — кнопка с общим числом источников. Клик открывает правую панель (drawer) со всеми источниками секции списком, без основного текста. Удобно когда нужно быстро проверить источниковую базу не читая текст. Drawer закрывается крестиком или кликом на затемнение.

Формат строки источника

Источник из API — plain-text строка, может содержать несколько URL через ;. Логика парсинга:

  • Разбивать по ; — каждый фрагмент — отдельная строка в списке
  • Если фрагмент содержит http — рендерить как кликабельную ссылку, отображать укороченный домен + стрелка ↗
  • Если фрагмент не содержит URL — рендерить как обычный текст (нормативный акт, например «UKLR 6.4.1»)
  • Не обрывать источник по длине — показывать полностью
Важно: если у секции нет ни одного источника (source: null или пустая строка) — кнопку источников не показывать вообще. Не показывать «0 источников».

Источники в сравнительной таблице

В сравнительной таблице на странице «По инструментам» источники в ячейках не отображаются — только значения параметров. Источники доступны в детальном виде конкретного режима (/venues/:venue_key/:cell_id). Исключение: tooltip при hover на ячейку — можно показать ссылку «Источник: [url]» если источник у параметра один и короткий.

06 Страница площадки — ключевые решения

Подробная реализация — в прототипе venues/venue.html. Здесь — решения, которые не очевидны из прототипа.

Иерархия данных: venue → instrument → tier → phase

venue_key  (HKEX_GEM, LSE_Main_Market, ...)
 └── instrument_class  (equity, bond, fund, depositary_receipt)
      └── tier / cell_id  (flat или именованный тир)
           └── phase  (admission, continuing, suspension, delisting)
                └── sections[]  (текстовые блоки с источниками)
                └── parameters[]  (П01–П41 с значениями)

Sticky-вкладки инструментов — переключают видимую секцию на странице, не меняют URL venue_key. Карточки тиров — переход на /venues/:venue_key/:cell_id.

Нумерация фаз

В данных фазы имеют row_index от 1 до 4. Текущий UI показывает 2/3/4/5 — это артефакт. Нужно использовать row_key как идентификатор и row_label как отображаемое название. Числовой префикс в UI не показывать.

Статусы верификации

Код APIОтображениеЦвет бейджа
greenВерифицированоЗелёный (sb-green)
yellowПроверить источникиОранжевый (sb-yellow)
redНенадёжноКрасный (sb-red)
unknownСтатус неизвестенСерый, без точки

Статус агрегируется по принципу worst-case: если хотя бы одна фаза red — итоговый red; если есть yellow — yellow; только если все green — итоговый green.

Переключатель «Вид: матрица / Вид: вкладки»

Кнопка в правом верхнем углу детального вида. Матричный вид — таблица phase × aspect, в ячейках — те же параметровые пилюли. Клик на ячейку матрицы переключает на вкладочный вид с открытой нужной фазой. Аспекты (столбцы матрицы) фиксированы: Требования / Процедуры / Мониторинг и надзор / Санкции / Раскрытие информации. Ячейки «Не применимо» — status: not_applicable из API, отображаются тире и некликабельны.

07 Страница «По инструментам» — ключевые решения

Подробная реализация — в прототипе instruments/instruments.html. Дополнения:

Layout: полная ширина окна

В отличие от страниц площадки, где контент ограничен max-width: 1060px, страница инструментов использует max-width: 1600px — из-за широкой сравнительной таблицы и левой панели. Левая панель — 280px фиксированная ширина, sticky, высота = viewport минус nav минус sticky-карточки инструментов. Правая область — оставшееся пространство, горизонтальный скролл таблицы при необходимости.

Карточки инструментов (sticky)

Четыре карточки — одновременно обзорная информация и переключатель активного инструмента. Карточка показывает: количество юрисдикций, количество листинговых режимов, топ-3 параметра по частоте встречаемости (из каталога параметров, поле «встречается в ячейках»). При смене инструмента — автоматически выбираются первые 3 режима для сравнения, сбрасывается поиск в левой панели, обновляется таблица.

Левая панель: логика фильтрации

  • Фильтры по правовой семье и типу площадки — мультиселект (можно выбрать несколько). При выборе «Все» — остальные сбрасываются.
  • Поиск — мгновенный (debounce 150ms), ищет по названию площадки и юрисдикции.
  • Чекбоксы режимов — без ограничения на количество выбранных. При выборе 0 — таблица показывает empty state.
  • Счётчик выбранных режимов обновляется в реальном времени.

Сравнительная таблица

Строки — выбранные листинговые режимы (venue + tier). Первая колонка — sticky по горизонтали при скролле таблицы. Столбцы — параметры, выбранные кнопками над таблицей. По умолчанию — топ-параметры для текущего инструмента и фазы (из частоты встречаемости). Значения параметров — строковые, ранжирование не предусмотрено. Пустое значение → тире.

Ограничение текущей реализации: данные в прототипе — заглушки. При реализации столбцы-параметры формируются динамически из реальных данных по выбранному инструменту и фазе. Набор параметров может существенно отличаться по инструментам.

08 Общие требования к реализации

CSS-токены

Все CSS-переменные из прототипов (--accent, --bg, --font-mono и т.д.) переносятся в глобальный :root без изменений. Шрифты: IBM Plex Sans, IBM Plex Mono, Newsreader — подключать через Google Fonts или локально.

Адаптивность

Прототипы спроектированы для десктопа (min-width ~1100px). Мобильная адаптация — вне текущего скоупа, но верстка не должна ломаться на 768px: допустим горизонтальный скролл таблиц, collapsed левая панель.

Состояния загрузки

Каждый компонент, получающий данные асинхронно, должен иметь skeleton-состояние (серые placeholder-блоки нужной формы). Не использовать спиннер на весь экран — только локально в изменяющемся блоке.

Пустые состояния

Если по выбранным фильтрам нет данных — показывать информативный empty state с объяснением причины и призывом к действию (например, «Нет режимов — снимите фильтры»). Пустой блок без сообщения — недопустим.

Доступность

Интерактивные элементы (div onclick=... в прототипе) в продакшене реализовывать через <button> или <a> с корректными aria- атрибутами. Таблицы — с <th scope>. Sticky-элементы не должны перекрывать фокус при Tab-навигации.

Приоритет реализации: (1) venue.html — страница площадки, (2) instruments.html — сравнительный вид. Страница площадки — критический путь, через неё проходит основная часть пользовательских сценариев.

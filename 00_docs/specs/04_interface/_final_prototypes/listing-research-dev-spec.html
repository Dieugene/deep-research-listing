ТЗ для разработчика: Listing Research Frontend

Версия 1.0 Март 2026 Статус: передаётся вместе с прототипами

Обзор задачи

Этот документ — руководящий документ для разработчика, который реализует фронтенд Listing Research на основе HTML-прототипов. Документ не описывает визуальный дизайн повторно — всё это уже реализовано в прототипах. Задача документа — передать принципы, которыми нужно руководствоваться, когда реальность не совпадает с прототипом.

Ключевая установка: прототипы работают с тестовыми данными (2–3 юрисдикции, 3–7 источника на блок). Реальные данные масштабнее и могут быть структурированы иначе. Прототип — это дизайн-эталон, а не жёсткая схема данных.

Прилагаемые файлы

Это ТЗ охватывает лендинг, список юрисдикций и карточку юрисдикции. По карточке торговой площадки и разделу инструментов будет отдельное ТЗ от второго дизайнера — дождись его перед началом работы над этими разделами.

Единственный источник истины по дизайн-системе: файл listing-research-design-handoff.html — CSS-переменные, шрифты, токены, компоненты. Сверяйся с ним при любых сомнениях по визуалу.

Расхождение данных с прототипом

Прототипы создавались до полной выгрузки реальных данных. Возможны следующие типы расхождений:

Тип расхожденияЧто делать
Другое название поля Замапить на нужный UI-элемент по смыслу. Документировать маппинг в коде через комментарий.
Поле отсутствует для части юрисдикций Показывать — или скрывать строку. Не показывать пустые блоки с заголовком без данных.
Поле есть, но его нет в прототипе Добавить в подходящий блок, придерживаясь визуального языка дизайн-системы. При сомнениях — эскалировать.
Структура данных принципиально отличается Эскалировать. Не изобретать структуру самостоятельно.
Данных значительно больше, чем в прототипе Применять паттерны масштабируемости (см. ниже). При сомнениях — эскалировать.
Данные есть, но смысл поля неясен Эскалировать. Не интерпретировать самостоятельно.

Паттерны масштабируемости

Все прототипы изначально спроектированы с расчётом на масштаб. Нужно проверить, что следующие вещи работают корректно при реальных данных:

  • Список юрисдикций: при 47+ строках пагинация (уже реализована в прототипе, 15 строк/страница).
  • Миникарточки площадок в правой колонке карточки юрисдикции: при 1 площадке — одна карточка без пустоты, при 10+ — список со скроллом внутри правой колонки (не растягивать всю страницу).
  • Таймлайн регуляторного анализа: при 27+ событиях (Гонконг) каждое событие на отдельной строке — это предусмотрено алгоритмом, нужно убедиться, что канвас корректно растягивается вертикально.
  • Маппинг терминов: аккордеон по группам — раскрывать только первую по умолчанию.

Протокол эскалации

⚠ Когда и как эскалировать

Если ты не понимаешь, как соотнести реальные данные с прототипом, не придумывай решение самостоятельно — создай файл-отчёт и сообщи мне.

Формат файла-отчёта

Файл называется ESCALATION_[раздел]_[дата].md, например: ESCALATION_jurisdiction_card_2026-04-01.md

Структура файла:

# Эскалация: [название раздела/страницы]

## Проблема
[Одна-две фразы: в чём расхождение]

## Что есть в прототипе
[Что ожидалось согласно прототипу]

## Что есть в реальных данных
[Что фактически пришло из API / базы]

## Варианты решения (опционально)
[Если у тебя есть идеи — перечисли, но не реализуй]

## Что заблокировано
[Какие именно компоненты/страницы нельзя завершить до ответа]

После создания файла — немедленно сообщи мне в рабочем канале: «Эскалация по разделу [X], файл [имя файла]». Не жди следующего статуса.

Важно: эскалация — это нормально и ожидаемо. Прототипы создавались до полного доступа к данным, расхождения заложены в риски проекта. Лучше потерять день на эскалацию, чем реализовать неверную структуру и переделывать.

Система источников

Это один из самых критичных UX-принципов продукта. Каждый блок данных должен иметь доступные источники. Прототипы показывают 2–4 источника на блок — в реальности их может быть 10–20.

Архитектура системы источников

1
Суперскрипт в тексте
Для точечных ссылок внутри текстового блока. Кликабельный суперскрипт [1], при клике — плавный скролл к списку внизу карточки с подсветкой.
2
Кнопка блока
«N источников» в шапке карточки-блока. Показывает общее количество. Открывает раздел источников.
3
Список внизу карточки
Пронумерованный список с названием документа и кликабельной ссылкой. Сворачивается если > порога.

Правило отображения при большом количестве источников

Применяй следующую логику в зависимости от количества источников на блок:

Кол-во источниковПоведение
1 – 5 Показывать все источники сразу в развёрнутом виде внизу карточки. Дополнительных действий не требуется.
6 – 15 Показывать первые 5, остальные скрыты за кнопкой «Показать ещё N». Клик — разворачивает всё, кнопка меняется на «Свернуть».
16+ Кнопка «N источников» в шапке блока открывает модальное окно (или тот же drawer-паттерн из таймлайна) с полным прокручиваемым списком источников, поиском и фильтром по типу документа.

Приоритет: источники — не сноски, они часть интерфейса. Пользователь-регулятор обязан всегда понимать, откуда взяты данные. Не прятать их слишком глубоко.

Формат данных источника (ожидаемый)

{
  "id": "src-001",
  "label": "FCA UK Listing Rules (UKLR) sourcebook",  // отображаемое название
  "url": "https://www.fca.org.uk/...",                // ссылка
  "type": "rulebook",  // тип: rulebook | legislation | consultation | report | other
  "year": 2024,        // опционально
  "note": ""           // опциональный комментарий к источнику
}

Если структура источника в базе отличается от ожидаемой — эскалировать.

Стартовый лендинг

Прототип: listing-research-landing-v2.html

Специфика реализации

  • Страница занимает ровно один viewport — вертикальный скролл отсутствует (overflow: hidden на html, body).
  • Карта — SVG, встроенный в HTML. Точки на карте должны быть кликабельными и открывать карточку-превью соответствующей юрисдикции. В прототипе показан пример одной статической карточки — в продакшне карточка подтягивается динамически.
  • Статистические цифры (47, 65, 4, ~1000) должны подтягиваться из API, не хардкодиться.
  • Dropdown меню «Справочник» — два пункта: «По юрисдикциям» и «По инструментам». Оба активны, без пометки SOON.
  • Пункты «Главная» и «Каталог параметров» в навигации отсутствуют.

Строки без данных

Строки со статусом empty визуально dimmed (opacity ~0.55), курсор default, кнопка заменяется на «Скоро». При наличии статуса partial — строка кликабельна, открывает карточку с имеющимися данными.

Сортировка по умолчанию

Первичная сортировка: data_status (full → partial → empty). Вторичная: priority (high → med → low).

Карточка юрисдикции

Прототип: jurisdiction-v3.html

Структура вкладок

Три вкладки: Юрисдикция / Регуляторный анализ / Термины. Отдельной вкладки «Площадки» нет — площадки встроены в вкладку «Юрисдикция» как миникарточки в правой колонке.

Вкладка «Юрисдикция» — первый экран

Двухколоночный layout: левая колонка (flex: 1) — одна карточка с двумя секциями «Архитектура допуска» и «Регулятор» через разделитель. Правая колонка (ширина ~340px) — стек миникарточек площадок.

Миникарточка площадки — точка входа на страницу площадки. Весь ряд кликабелен, включая стрелку →. При hover: border-color → accent, box-shadow.

Вкладка «Регуляторный анализ»

Два режима: Таймлайн (по умолчанию) и Список. Переключатель внутри вкладки.

Данные события регуляторного анализа

{
  "id": "evt-001",
  "type": "problem",       // problem | contra | reform | tool
  "start": 2013,           // год начала
  "end": 2024,             // год окончания (= start если точечное событие)
  "label": "...",          // короткий лейбл для таймлайна (≤ ~30 символов)
  "title": "...",          // заголовок для drawer/списка
  "text": "...",           // основной текст на русском
  // Только для type=contra:
  "conflict": {
    "a": { "label": "...", "text": "..." },
    "b": { "label": "...", "text": "..." }
  },
  "resolution": "...",     // текст разрешения противоречия
  "sources": [...]         // массив источников
}

Таймлайн — параметры рендеринга

JS-константы вынесены в начало функции renderTimeline(). Если при реальных данных элементы накладываются — увеличивать LANE_H с шагом 4px до устранения наложений.

Drawer детализации

Открывается при клике на любой элемент таймлайна или его подпись. Закрывается крестиком или кликом по backdrop. Backdrop начинается на top: 112px (под nav 56px + tabs 56px) — это принципиально, иначе закрывает навигацию. Drawer использует visibility: hidden / visible вместо просто transform, потому что overflow-x: hidden на body не скрывает position: fixed элементы.

Институциональные метрики (WGI/WDI)

Данные пока отмечены как placeholder. При подключении реальных данных использовать поля WGI (Rule of Law, Regulatory Quality, Government Effectiveness) и WDI индикатор CM.MKT.LCAP.GD.ZS (Market Cap / GDP). Прогресс-бар нормируется к максимальному значению в выборке, не к фиксированному максимуму.

Кластеризация

Чипы «Схожих юрисдикций» кликабельны — ведут на карточку соответствующей юрисдикции. Коэффициент сходства отображается как число 0.xx в мелком моно-тексте.

Карточка торговой площадки (venue)

Этот раздел покрывается отдельным ТЗ от второго дизайнера. Не приступай к реализации до получения этого ТЗ с прототипами. Ниже — только связующие принципы, которые нужно учесть.

Связь с карточкой юрисдикции

Площадка — дочерняя сущность юрисдикции. Навигация: Справочник → Юрисдикция → Площадка. Breadcrumb: Главная › Справочник › [Юрисдикция] › [Площадка].

Иерархия данных

Используется трёхуровневая иерархия: Оператор → Площадка (Venue) → Тир/Сегмент. Если реальная структура отличается — эскалировать, не адаптировать самостоятельно.

Параметры листинга (П01–П41)

На карточке площадки отображаются значения параметров из словаря (41 параметр, 5 групп). Каждая ячейка параметра имеет источники — применять систему источников согласно разделу выше. Пустые ячейки (данные не собраны) — показывать — без скрытия строки.

Инструменты

Этот раздел покрывается отдельным ТЗ от второго дизайнера. Не приступай к реализации до получения этого ТЗ с прототипами. Ниже — только связующие принципы.

Навигация

Переход из главной страницы: кнопка «Инструменты». Из навигации: Справочник → «По инструментам». Четыре класса: акции, облигации, фонды, депозитарные расписки.

Интеграция с юрисдикциями

Детальное отображение инструмента включает привязку к юрисдикциям. Кросс-ссылки между карточкой инструмента и карточкой юрисдикции должны работать в обоих направлениях.

Навигация — итоговая структура

Пункт менюПоведениеСтатус
СправочникDropdown: «По юрисдикциям» + «По инструментам»Активно
АнализНедоступно, бейдж SOONSOON
АссистентНедоступно, бейдж SOONSOON
ГлавнаяОтсутствует в менюУбрать
Каталог параметровОтсутствует в менюУбрать

На всех страницах кроме лендинга навигация sticky с top: 0; z-index: 200. На лендинге — position: fixed. Вкладки страницы (page-tabs) sticky с top: 56px; z-index: 100.

Дизайн-система — критичные правила

Полная документация в listing-research-design-handoff.html. Здесь — только то, что чаще всего нарушают при реализации.

  • Шрифты — три, строго: Newsreader (заголовки страниц), IBM Plex Sans (интерфейс), IBM Plex Mono (метки, числа, теги, код). Не заменять на system fonts.
  • Светлая тема — основная. Тёмная тема реализована только на лендинге.
  • Карточки: box-shadow: 0 1px 4px rgba(0,0,0,.08), 0 0 0 0.5px rgba(0,0,0,.04) — двойная тень для чёткости границ. Без этого карточки сливаются с фоном.
  • Флаги — не emoji: на лендинге SVG Union Jack. В списке юрисдикций emoji допустимы как fallback, но желательно SVG через flagcdn.com или аналог.
  • Анимации: fadeInUp только при первом рендере страницы, не при каждом роутинге.
  • overflow-x: hidden на html, body обязателен — иначе drawer выглядывает из-за правого края.

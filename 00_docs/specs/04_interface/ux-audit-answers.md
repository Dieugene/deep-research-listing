# Listing Research — Ответы на вопросы UX-аудита
**Март 2026 · v1.0 · Ответы разработчика данных**

---

## 2.1 Тиры, сегменты, инструменты

### Q-01 — Иерархия площадки

**Как устроена иерархия внутри площадки в БД?**

Поля `venue.tiers[]` и `venue.segments[]` архитектурно зарезервированы, но пайплайном Level 2 **не заполняются** — они всегда пустые массивы.

Фактическая иерархия реализована иначе: каждый `cell_id` содержит поле `tier`, которое описывает тир/режим допуска на уровне ячейки. Примеры из LSE Main Market:

| cell_id | tier |
|---|---|
| `GB_LSE_Main_Market_equity_shares_commercial_compa_equity` | `Equity Shares (Commercial Companies)` |
| `GB_LSE_Main_Market_equity_shares_international_co_equity` | `Equity Shares (International Commercial Companies Secondary Listing)` |
| `GB_LSE_Main_Market_equity_shares_transition_equity` | `Equity Shares (Transition)` |

При плоской структуре (нет тиров) поле принимает значение `"(no listing tiers — flat structure)"` — как у HKEX GEM.

**AIM и SFM** — это **отдельные `venue_key`**, а не тиры внутри LSE Main Market. Каждая торговая площадка имеет собственный `venue_key` и собственный набор ячеек.

---

### Q-02 — Схема формирования cell_id

**Формула:**
```
{country_code}_{venue_key}_{tier_slug}_{instrument_class}
```

- `country_code` — двухбуквенный код юрисдикции (GB, HK, AU, SI, FR, GE…)
- `venue_key` — ключ площадки (LSE_Main_Market, HKEX_GEM…)
- `tier_slug` — слаг из значения поля `tier` (нормализация пробелов, обрезка до ~40 символов)
- `instrument_class` — класс инструмента (equity, bond…)

**Примеры:**

| Площадка | Тир | Инструмент | cell_id |
|---|---|---|---|
| HKEX GEM | (плоская) | equity | `HK_HKEX_GEM_equity` |
| LSE Main Market | Equity Shares (Commercial Companies) | equity | `GB_LSE_Main_Market_equity_shares_commercial_compa_equity` |
| LSE Main Market | Equity Shares (Transition) | equity | `GB_LSE_Main_Market_equity_shares_transition_equity` |

Когда тир отсутствует, `tier_slug` опускается и cell_id имеет три сегмента вместо четырёх.

---

### Q-03 — Значения instrument_class

Текущий полный список в БД (по всем юрисдикциям):

| Ключ | Отображаемое название |
|---|---|
| `equity` | Акции |
| `bond` | Облигации |
| `fund` | Фонды |
| `depositary_receipt` | Депозитарные расписки |

Список **расширяется через новые cell_id** — при добавлении новых инструментов в пайплайн генерируются ячейки с новым значением `instrument_class`. Изменений в схеме существующих ячеек не требуется.

ETF, конвертируемые облигации, структурированные продукты в текущей БД отсутствуют — в планах при запуске соответствующих юрисдикций.

## 2.2 Матрица ячеек: фазы и аспекты

### Q-04 — Нумерация фаз

Нумерация фаз 2/3/4/5 в UI — **артефакт рендеринга**, не семантика данных. В модели данных (`MatrixRow.row_index`) фазы нумеруются **с 1**:

| row_index | row_key | Отображаемое название |
|---|---|---|
| 1 | `admission` | Первичный допуск |
| 2 | `continuing` | Поддержание листинга |
| 3 | `suspension` | Приостановка |
| 4 | `delisting` | Исключение из списка |

**Фазы 1 не существует** в пайплайном смысле. Видимые 2/3/4/5 — результат того, что UI добавляет +1 к `row_index`. Рекомендация: убрать числовой префикс из UI или исправить на правильный индекс 1-4.

---

### Q-05 — Аспекты (столбцы матрицы)

Список **фиксированный**, 5 аспектов для всех площадок и инструментов:

| col_index | col_key | Отображаемое название |
|---|---|---|
| 1 | `requirements` | Требования |
| 2 | `procedures` | Процедуры |
| 3 | `monitoring` | Мониторинг и надзор |
| 4 | `sanctions` | Санкции |
| 5 | `disclosure` | Раскрытие информации |

Заполненность каждой ячейки зависит от фазы — не все аспекты применимы ко всем фазам. Например, мониторинг и санкции недоступны на фазе первичного допуска (статус `not_applicable`). Это задано жёстко в бэкенде, не в данных.

---

### Q-06 — «н/п» vs «нет данных»

Это два принципиально разных статуса (`MatrixCellStatus`):

| Статус | Код | Смысл |
|---|---|---|
| Не применимо | `not_applicable` | Аспект **архитектурно** не применим к данной фазе (например, мониторинг при первичном допуске). Задаётся жёстко в бэкенде, не в данных. |
| Нет данных | `not_filled` | Аспект применим, но **данные ещё не собраны** пайплайном. |
| Заполнено | `filled` | Данные есть. |

В API каждая ячейка матрицы (`MatrixColumn`) возвращает поле `status` с одним из трёх значений выше.

## 2.3 Контент ячейки (drawer)

### Q-07 — Структура объекта ячейки

Контент ячейки возвращается по эндпоинту `/api/cells/{jurisdiction}/{venue_key}/{cell_id}/content`.

**Верхний уровень:**
```json
{
  "cell_id": "HK_HKEX_GEM_equity",
  "venue_key": "HKEX_GEM",
  "tier": "(no listing tiers — flat structure)",
  "instrument_class_key": "equity",
  "instrument_class_label": "Акции",
  "phases": [ ... ]
}
```

**Каждая фаза** (`PhaseContent`):
```json
{
  "phase_key": "admission",
  "phase_label": "Первичный допуск",
  "has_data": true,
  "validation_status": "green",
  "sections": [ ... ]
}
```

**Каждый раздел** (`ContentSection`) — самостоятельный текстовый блок с источником:
```json
{
  "section_key": "instrument_requirements",
  "section_label": "Требования к инструменту",
  "text": "Free‑float requirement (Rule 11.23A)...",
  "source": "https://en-rules.hkex.com.hk/rulebook/1123a"
}
```

**Фазы:** 3 (admission = 3A, maintenance = 3B, enforcement = 3C).

**Возможные секции** в каждой фазе (не все присутствуют в каждой ячейке):

| section_key | Название |
|---|---|
| `admission_overview` | Общий обзор допуска |
| `eligibility_requirements` | Требования к эмитенту |
| `instrument_requirements` | Требования к инструменту |
| `procedure_and_timeline` | Процедура и сроки |
| `disclosure_at_admission` | Раскрытие информации при допуске |
| `secondary_admission` | Вторичный допуск |
| `special_regimes` | Специальные режимы |
| `restrictions_and_lock_ups` | Ограничения и lock-up |
| `sponsor_and_infrastructure` | Спонсор и инфраструктура |
| `common_requirements_common` | Общие требования |
| `additional_findings` | Дополнительные сведения |

Набор секций **не фиксирован** — зависит от содержания источников для конкретной ячейки.

---

### Q-08 — Параметры П01–П41 и их привязка к ячейкам

Параметры хранятся в `pass2_ru.json` на уровне `cell_id`. **Привязки к аспектам матрицы нет** — параметр привязан к ячейке целиком и к фазе жизненного цикла.

**Структура записи параметра:**
```json
{
  "parameter_id": "P01",
  "parameter_name": "Free float / Public float / Shares in public hands",
  "lifecycle_phase": "admission",
  "value": "25%...",
  "calculation_methodology": "...",
  "alternatives": "...",
  "variations": "...",
  "linkages": ["P02", "P03"],
  "source": "GEM Rules 11.23(2)(a)",
  "status": "found",
  "note": "...",
  "drill_down_applied": true
}
```

Один параметр может встречаться несколько раз с разными `lifecycle_phase` (например, P01 присутствует для фаз admission, continuing, delisting).

**Маппинг параметр → аспект отсутствует.** Вкладка «Параметры» в drawer — это плоский список всех параметров ячейки, сгруппированных по `lifecycle_phase`.

**Возможные статусы параметра:**

| Статус | Смысл |
|---|---|
| `found` | Параметр найден и заполнен |
| `not_found` | Параметр не обнаружен в источниках |
| `not_applicable` | Параметр не применим для данной ячейки |

---

### Q-09 — Источники и гранулярность

Источники хранятся на **двух уровнях**:

1. **Секция контента** (`ContentSection.source`) — строка с URL или нормативной ссылкой, привязана к конкретному текстовому блоку внутри ячейки.
2. **Параметр** (`ParameterValue.source`) — строка с источником, привязана к конкретному значению параметра в конкретной фазе.

Источника на уровне «всей ячейки» нет — только на уровне текстового раздела или параметра.

**Формат:** plain text строка (может содержать несколько URL через `;`), не структурированный объект.

---

### Q-10 — Индикатор объёма (10.3k / 8.7k / 19.5k)

`text_volume` — количество **символов** в соответствующем raw JSON-файле (3A, 3B или 3C). Это технический показатель: считается длина всего JSON (включая ключи, скобки, пробелы) — не только тексты описаний.

- Учитывается текст того языка, на котором хранится файл (для большинства ячеек — английский 3X_raw.json или русский pass2_ru.json)
- Показатель даёт приблизительную оценку «насыщенности» данных, а не точный объём читаемого текста

**Рекомендация:** заменить на пользовательски значимый статус (верифицировано / данные есть / нет данных) на основе `validation_status` и `has_data`.

## 2.4 Временные периоды и версионирование

### Q-11 — Версионирование данных

**Версионирования нет.** Данные в ячейках хранятся как **текущее состояние** на момент последнего запуска пайплайна.

- Нет полей `valid_from` / `valid_to` ни на уровне ячейки, ни на уровне секции
- Дата сбора данных доступна косвенно через поле `retrieved_at` в raw-файлах (ISO-8601, UTC)
- При повторном запуске пайплайна данные перезаписываются

Историческое версионирование (например, «до реформы UKLR 2024» / «после») в текущей модели данных **не реализовано**. Это осознанное ограничение: база хранит актуальное состояние, а не историю изменений.

---

### Q-12 — Period tag (периоды действия требований)

Поля для периода на уровне подраздела ячейки **нет**. Period-теги (`"2013–2024"` и т.п.) в текущей модели данных не предусмотрены на уровне секций контента.

Поле `period` существует только в **L4-данных** (уровень юрисдикции):
- `problems[].period` — период проблемы
- `contradictions[].period` — период противоречия
- `parameters_as_tools[].period` — период
- `reforms[].year` — год реформы (другое поле — известное расхождение в модели)

Если period-теги нужны на уровне отдельных требований — это потребует расширения модели данных пайплайна.

## 2.5 Статусы верификации

### Q-13 — Validation status: логика и значения

Статус вычисляется **автоматически пайплайном** (не выставляется аналитиком вручную) по трём критериям из файла `3X_validation.json`:

| Критерий | Поле | Смысл |
|---|---|---|
| Тематическое соответствие | `scope_ok` | Данные покрывают ожидаемые темы для данной ячейки |
| Полнота | `completeness_score` | Оценка 0.0–1.0 по покрытию обязательных тем |
| Качество источников | `source_ok` | Источники — официальные нормативные документы, не вторичные |

**Возможные значения:**

| Статус | Код | Смысл | Рекомендуемый бейдж |
|---|---|---|---|
| Верифицировано | `green` | Все три критерия выполнены | «Верифицировано» |
| Требует проверки | `yellow` | Частичные проблемы (неполное покрытие или спорные источники) | «Частично верифицировано» |
| Ненадёжно | `red` | Серьёзные проблемы с данными или источниками | «Ненадёжно» |
| Неизвестен | `unknown` | Валидационный файл отсутствует | — |

Статус агрегируется по принципу «worst-case» при отображении ячейки матрицы: если хотя бы один из трёх файлов (3A/3B/3C) имеет `red` — итоговый статус `red`; если есть `yellow` — `yellow`; только если все `green` — итоговый `green`.

## 3. Дополнительные наблюдения для UX-проектирования

| Тема | Наблюдение |
|---|---|
| API эндпоинты ячейки | 404 при внешнем аудите — ожидаемо. Контент ячейки: `/api/cells/{jurisdiction_ru}/{venue_key}/{cell_id}/content`, матрица: `/api/cells/{jurisdiction_ru}/{venue_key}/{cell_id}/matrix`, параметры: `/api/cells/{jurisdiction_ru}/{venue_key}/{cell_id}/parameters` |
| `listing_architecture` | Поле предусмотрено в модели, но пайплайном не заполняется. Описательная информация об архитектуре допуска сейчас находится в секциях `admission_overview` и `special_regimes` внутри контента ячейки. |
| `secondary_listing_regime` | Флаг `true` означает, что данная ячейка описывает режим вторичного листинга (например, HKEX Chapter 19C). В UI рекомендуется маркировать такие ячейки/тиры визуально. |
| `instrument_coverage[]` | Поле есть в venue_card, содержит `notes_ru`/`notes_en`. Поля `admission_path` и `regime_name` не заполняются. |
| Нумерация фаз | Числовые префиксы 2/3/4/5 в текущем UI — артефакт. Рекомендуется убрать: `row_index` в данных равен 1–4, а лейблы фаз уже описательны. |

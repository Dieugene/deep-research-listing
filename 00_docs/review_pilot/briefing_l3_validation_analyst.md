# Брифинг для аналитика: диагностика L3-валидации

**Назначение:** Ты — аналитик пайплайна исследования. Твоя задача — разобраться, почему 38 из 74 ячеек не прошли валидацию после L3-ресёрча. Ниже — полный контекст проекта, архитектура пайплайна, известные проблемы и что именно нужно проверить.

---

## 1. Что это за проект

Банк России проводит масштабное сравнительное исследование подходов к листингу ценных бумаг в 47 юрисдикциях и ~120 торговых площадках (venue). Данные собираются через Parallel Task API (deep research) по многоуровневому пайплайну и затем обрабатываются LLM.

Пилот выполнен по двум юрисдикциям: Великобритания (LSE Main Market, LSE AIM, Aquis Stock Exchange) и Гонконг (HKEX Main Board, HKEX GEM). Итого 5 venue, 26 ячеек, 74 L3-задачи.

---

## 2. Архитектура пайплайна (уровень 3)

### Единица запроса
venue × instrument_class (все тиры/категории одного класса инструмента на venue в одном запросе). Процессор: pro.

### Три запроса по тематике (параллельно):
- **L3-A:** первичный допуск (требования, процедуры, раскрытие, спецрежимы)
- **L3-B:** негативные аспекты (поддержание обязательств, приостановка, исключение/делистинг)
- **L3-C:** мониторинг и enforcement (надзор, санкции, дисциплинарные процедуры)

### Формат результата
JSON schema с массивом `tiers[]`. Каждый элемент — данные по одному тиру/категории. Parallel заполняет столько элементов, сколько тиров найдёт. После — LLM-постобработка разносит элементы массива по конкретным ячейкам (venue × tier × instrument_class).

### Валидация
После постобработки — LLM-валидация по каждой ячейке. Три проверки:
- **scope_ok:** основной предмет результата соответствует target venue/tier/instrument_class. Сравнительные упоминания других площадок ДОПУСТИМЫ. Fail — только если основной контент описывает ДРУГУЮ venue/tier.
- **completeness_score:** доля покрытых топиков из чеклиста для данной пары (instrument_class, query_type). Чеклист двумерный: instrument_class × query_type (3A/3B/3C).
- **source_ok:** источники (rulebook chapters, regulations) соответствуют target venue/tier.

overall_flag=True (REVIEW NEEDED) ставится при scope=False, completeness < 0.5, или source=False.

## 3. Ключевые понятия

### Иерархия объектов
- **Operator** (Б02): институт, управляющий площадками. Пример: London Stock Exchange Group.
- **Venue** (А02): площадка с собственной регуляторной рамкой и rulebook. Пример: LSE Main Market (Regulated Market), AIM (MTF) — это РАЗНЫЕ venue одного оператора.
- **Listing tier** (А05): иерархический уровень внутри venue (строже/мягче). Пример: Premium/Standard (до реформы 2024 на LSE).
- **Segment** (А04): тематическая надстройка (ESG, SME, tech). Не иерархия строгости.
- **Modifier**: модификация стандартного режима для типа эмитента (SPAC, WVR, biotech). НЕ порождает отдельную ячейку.

### Архитектура допуска (Г04)
- **merged:** листинг и допуск к торгам — единая процедура (большинство юрисдикций, Гонконг).
- **split:** листинг (включение в Official List, FCA/UKLA) и допуск к торгам (решение биржи LSE) — разные правовые акты. Великобритания.

### UK-специфика (UKLR 2024)
После реформы 2024 LSE Main Market не имеет вертикальных тиров. Вместо них — UKLR-категории по классу инструмента:
- ESCC (Equity Shares — Commercial Companies) → UKLR 3, 6, Appendix 1
- Transition (Equity Shares — Transition) → UKLR 22 — **legacy-категория**, закрыта для новых эмитентов
- CEF (Closed-End Investment Funds) → UKLR 3, 16
- Debt → UKLR 3, 17
- Shell Companies → UKLR 3, 18 — это modifier, не отдельная категория
- DR (Depositary Receipts) → UKLR 3
- ATT Only (Admission to Trading Only) → LSE ADS, не UKLR — отдельный путь допуска (admission_path: "trading_only"), другой rulebook, другой надзорный орган

Два набора правил для UK:
- FCA UK Listing Rules (UKLR) — для Official List
- LSE Admission and Disclosure Standards (ADS) — для допуска к торгам на бирже

### HKEX-специфика
- Main Board: основной рынок, Listing Rules (Chapters 1–19C)
- GEM: Growth Enterprise Market, отдельный rulebook (GEM Listing Rules)
- Специальные главы (Chapter 8A WVR, 18A Biotech, 18B SPAC, 19C Secondary) — modifiers, не отдельные venue/tier
- HDR (Hong Kong Depositary Receipts) — специфический продукт HKEX, Chapter 19B

### Aquis Stock Exchange
Отдельная venue (не LSE). Regulated Market. Собственный rulebook (Aquis Exchange Listing Rules). Меньше покрытие в публичных источниках, чем у LSE.

## 4. Известные паттерны проблем (из отчёта тех.лида)

### Паттерн 1: source_ok=False — главная причина флажков
Много случаев scope=True, completeness=высокая, source=False. Источники не соответствуют ожидаемым главам для данного тира.

**Что проверить:**
- Какие именно источники цитируются? Правильные ли главы UKLR/ADS для данной UKLR-категории?
- Не перепутаны ли UKLR-категории (данные по Transition попали в ESCC, данные по Shell попали в DR)?
- Не смешаны ли FCA-источники и LSE-источники в одном поле?
- Для source check: как сформулирован промпт валидатора? Знает ли он, какие конкретно главы ожидаются для данной ячейки? Или оценивает «по ощущениям»?

### Паттерн 2: Aquis — все ячейки scope=False
Возможные причины:
- Parallel вернул контент, смешанный с LSE (Aquis малоизвестна, LSE доминирует в UK-результатах).
- LLM-постобработка некорректно разнесла данные между LSE и Aquis.
- Промпт для Aquis недостаточно чётко отграничивает от LSE.

**Что проверить:**
- Посмотреть raw-результат Parallel для Aquis (до постобработки): содержит ли он данные именно по Aquis Exchange Listing Rules, или по LSE/UKLR?
- Посмотреть промпт: достаточно ли чётко указано «Aquis Stock Exchange, NOT London Stock Exchange»?

### Паттерн 3: Transition-ячейки всегда падают
Ожидаемо. Transition — legacy-категория, закрыта для новых эмитентов. По ней не должен запускаться L3-A (первичный допуск). Если L3-A запущен — он найдёт мало данных и провалит completeness.

**Что проверить:**
- Запущен ли L3-A по transition-ячейкам? Если да — это ошибка в логике генерации задач (legacy-ячейки должны получать только L3-B + L3-C).
- Если L3-A не запущен, а проваливаются L3-B/L3-C — посмотреть, есть ли вообще continuing obligations для transition-категории (вероятно, мало).

### Паттерн 4: HKEX HDR — все query_type падают
HDR — специфический продукт HKEX, регулируется Chapter 19B Main Board Listing Rules. Малый объём публичных данных.

**Что проверить:**
- Есть ли в raw-результате Parallel данные по Chapter 19B вообще?
- Не подставлены ли данные по стандартным акциям вместо HDR?

## 5. Структура файлов

```
03_data/countries/
  {name_ru}/
    level_1/
      1A_raw.json          — raw-результат Parallel (архитектура юрисдикции)
      1B_institutional.json — институциональные факторы
      1C_raw.json          — ландшафт площадок
      jurisdiction_card.json — обработанная карточка юрисдикции
    level_2/
      {venue_key}/
        2A_raw.json        — raw-результат Parallel (структура площадки)
        venue_card.json    — обработанная карточка площадки
        cells_list.json    — перечень ячеек для L3
    level_3/
      {venue_key}/
        {cell_id}/
          3A_raw.json      — raw-результат Parallel (первичный допуск)
          3B_raw.json      — raw-результат Parallel (негативные аспекты)
          3C_raw.json      — raw-результат Parallel (мониторинг)
          3A_cell.json     — результат после постобработки (разнесение по ячейке)
          3B_cell.json
          3C_cell.json
          validation.json  — результат валидации
```

Промпты сохранены в /prompts/ (точный путь — уточнить в структуре проекта).

## 6. Что нужно сделать

### Шаг 1. Общая картина
Прочитать файл со сводкой валидации (validator output / лог) — определить, какие именно 38 ячеек провалились, по какому query_type, с какими значениями scope/completeness/source.

### Шаг 2. Source check — основная проблема
Для 3–5 ячеек с source_ok=False при высокой completeness:
- Открыть *_cell.json (результат после постобработки) — какие источники цитируются?
- Открыть *_raw.json (raw-результат Parallel до постобработки) — те же источники или постобработка что-то испортила?
- Открыть промпт валидатора — как сформулирован source check? Знает ли валидатор конкретные ожидаемые главы для данной ячейки, или судит абстрактно?
- Определить: это реальная проблема данных (Parallel нашёл не те главы) или ложноположительный source check (валидатор слишком строг)?

### Шаг 3. Aquis
- Открыть raw-результат Parallel для Aquis (3A_raw.json для любого класса инструментов)
- Проверить: данные по Aquis Exchange Listing Rules или по LSE/UKLR?
- Открыть промпт, который ушёл в Parallel для Aquis — достаточно ли чётко отграничен от LSE?

### Шаг 4. Transition
- Проверить cells_list.json для LSE Main Market — есть ли ячейка transition с пометкой legacy=true?
- Какие query_type по ней запущены (3A? 3B? 3C?)?

### Шаг 5. HDR
- Открыть raw-результат Parallel для HKEX HDR — есть ли ссылки на Chapter 19B?
- Если нет — Parallel не нашёл данных. Это ожидаемый пробел (мало публичной информации по HDR).

### Шаг 6. Выводы
По каждому паттерну: реальная проблема данных, проблема промпта, проблема валидатора, или ожидаемый пробел. Сформулировать рекомендации:
- Какие ячейки нужно перезапустить (с уточнённым промптом)?
- Какие ячейки — ожидаемый пробел (пометить «н/д» и двигаться дальше)?
- Нужны ли правки в валидаторе?

## 7. Принципы работы

- Не предполагай — проверяй файлы. Открой raw-результат, открой промпт, открой валидацию.
- Если нужно понять структуру проекта — начни с корневого каталога, найди где лежат файлы.
- Не пытайся исправить код — твоя задача диагностика. Результат — отчёт с конкретными находками и рекомендациями.
- Будь конкретен: «в файле X, поле Y содержит ссылку на UKLR 22, а должна быть UKLR 6» — а не «возможно, данные перепутаны».

## Архитектурный принцип: постобработка — часть пайплайна

> **Каждый шаг постобработки должен быть встроен в основной пайплайн (`run_pipeline.py`),
> а не существовать как отдельный инструмент или разовый скрипт.**

Это означает: когда добавляется новая юрисдикция или площадка и запускается полный прогон пайплайна,
на выходе должны автоматически быть получены те же результаты, что и у уже обработанных данных:
- матрица 4×5 по каждой ячейке L3
- pass2_ru.json с переведёнными параметрами
- источники с excerpts, привязанные к блокам данных
- обогащённые поля в jurisdiction_card.json, venue_card.json, level4.json

Задачи 006–014 при реализации должны создавать не только catch-up скрипты для существующих данных,
но и интегрированные шаги в `run_pipeline.py`, которые будут выполняться автоматически для любых новых данных.

**Прецедент:** Phase 2 translation не была встроена в пайплайн → при добавлении AU/DE/SG/FR
шаг был пропущен, данные остались без русского перевода параметров (обнаружено 2026-03-16).

## Примечания к задачам

### 006 — Phase 2 для AU/DE/SG/FR + встройка в пайплайн
Phase 2 (структурированное извлечение параметров + перевод на RU) выполнена только для UK и HK.
AU/DE/SG/FR не имеют ни `pass2.json`, ни `pass2_ru.json`.
Задача: запустить Phase 2 (pass1 → pass2 → translate) для 4 юрисдикций,
а также встроить шаг `run_pass2_translate` в основной `run_pipeline.py` —
чтобы перевод больше не пропускался при будущих запусках.
Phase 2 должна обходить юрисдикции через filesystem (не через state-файл пилота).

### 007 — Источники: excerpts + привязка к блокам
`add_citations.py` сохраняет только `{url, title, field}`, отбрасывая `excerpts`.
Parallel API возвращает реальные текстовые выдержки из нормативных документов — их нужно сохранять.
Привязка к блокам данных реализуется через `basis.field`:
каждый источник уже знает, какое поле схемы он обосновывает.
При построении матрицы L3 (задача 008) это поле используется для атрибуции источника к конкретной ячейке матрицы.
Для L1 — блок `architecture`/`regulator`/`notes`. Для L4 — требуется отдельный LLM-шаг (задача 010).

### 008 — L3 матрица 4×5
Преобразование 3A/3B/3C → структуру `matrix.json` по схеме:
- 4 строки: Г07.1 Первичный допуск / Г07.2 Поддержание / Г07.3 Приостановка / Г07.4 Исключение
- 5 столбцов: Д01 Требования / Д02 Процедуры / Д03 Мониторинг / Д04 Санкции / Д05 Раскрытие
Алгоритмический маппинг: ~80% полей — детерминированно по таблице из spec_matrix_mapping.md.
LLM-маппинг: sanctions (разбивка по фазам), monitoring (Г07.2 vs Г07.3), additional_findings.
Источники (задача 007) привязываются к ячейкам матрицы через basis.field → поле схемы → ячейка.
Спецификация: `00_docs/specs/05_pipeline/_ux-requirements/spec_matrix_mapping.md`

### 023 — Orphaned citations: чистка + защита (P3 из audit_pipeline.md)

- **Pipeline fix:** в логике записи L3 данных: если `description` пустой или `"not applicable"` — не записывать citations к этой секции, либо переносить их в `additional_findings` как fallback.
- **Catchup:** сканировать все `3A/3B/3C_raw.json`, найти ячейки с такими orphaned citations, перевязать или удалить.
- **Масштаб:** неизвестен до сканирования — возможно только EQUITY-3, возможно больше.

# Методология исследования

## О проекте

Listing Research — база данных требований к листингу ценных бумаг на биржах мира. Проект собирает, структурирует и анализирует регуляторные требования к допуску, поддержанию, приостановке и исключению ценных бумаг из листинга.

Данные собираются автоматизированным пайплайном на основе deep research AI (Parallel API) с последующей постобработкой, структурированием и переводом.

---

## 1. Охват исследования

### 1.1. Юрисдикции

Исследование охватывает юрисдикции с организованными рынками ценных бумаг. На текущем этапе обработаны:

| Юрисдикция | Правовая семья | Регулятор | Площадки |
|------------|---------------|-----------|----------|
| Австралия | Common law | ASX | 4 |
| Великобритания | Common law | FCA | 3 |
| Германия | Civil law | Deutsche Boerse AG | 5 |
| Гонконг | Common law | SEHK | 2 |
| Россия | Civil law | Банк России | — |
| Сингапур | Common law | SGX-ST | 1 |
| Франция | Civil law | Euronext Paris | 5 |

Перечень юрисдикций расширяется по мере продвижения исследования.

### 1.2. Площадки

20 площадок, включая регулируемые рынки (Regulated Markets), многосторонние торговые системы (MTF) и рынки, регулируемые биржей (Exchange Regulated Markets).

### 1.3. Ячейки исследования

Минимальная единица исследования — **ячейка** (cell): пересечение площадки, тира листинга и класса инструмента.

Четыре класса инструментов:
- **equity** — акции
- **bond** — облигации
- **fund** — фонды и ETF
- **depositary_receipt** — депозитарные расписки

Всего: **~105 ячеек** по всем юрисдикциям.

## 2. Архитектура сбора данных

### 2.1. Уровни исследования

Данные собираются на четырёх уровнях, каждый из которых отвечает на свой класс вопросов:

| Уровень | Объект | Что исследуется | Источник |
|---------|--------|----------------|----------|
| **L1** | Юрисдикция | Регуляторная архитектура, институциональный фреймворк, перечень площадок | Parallel API (pro) |
| **L2** | Площадка | Структура площадки: тиры, сегменты, покрытие инструментов | Parallel API (pro) |
| **L3** | Ячейка | Детальные требования по трём фазам: допуск (3A), поддержание/приостановка/исключение (3B), мониторинг и enforcement (3C) | Parallel API (pro) |
| **Phase 2** | Ячейка | Извлечение количественных параметров из контента L3 | LLM (gpt-5) |
| **L4** | Юрисдикция | Аналитика: проблемы, противоречия, реформы, параметры как инструменты | Parallel API (pro) |

### 2.2. Parallel API

Parallel API — инструмент глубокого исследования (deep research), который автономно ищет информацию в интернете, анализирует найденные документы и формирует структурированный ответ.

Для каждого запроса API возвращает:
- **content** — структурированный ответ (текст или JSON)
- **basis[]** — массив обоснований: для каждой секции ответа — reasoning (логика рассуждения), citations (ссылки на документы) и excerpts (выдержки из документов)
- **confidence** — уровень уверенности (high / medium / low)

Excerpts — это прямые цитаты из найденных документов, на которых основаны выводы. Они позволяют верифицировать каждое утверждение.

### 2.3. LLM-обработка

Для задач, не требующих deep research (извлечение параметров, переводы, классификация), используются модели LLM:

| Модель | Задачи |
|--------|--------|
| **gpt-5** (SMART) | Извлечение параметров из текста (Phase 2), аналитика L4 |
| **gpt-5-mini** (FAST) | Переводы, классификация типов источников, распределение санкций по фазам матрицы |

LLM не используется для задач, решаемых алгоритмически (нормализация, очистка артефактов, маппинг секций).

## 3. Процесс сбора и обработки

### 3.1. Level 1 — Юрисдикция

**Три запроса к Parallel API:**

| Запрос | Что исследуется | Формат ответа |
|--------|----------------|---------------|
| **1A** | Регуляторная архитектура: кто регулирует листинг, какова правовая основа, как устроен процесс допуска | Свободный текст |
| **1B** | Институциональный фреймворк: качественные факторы, влияющие на листинг (судебная система, корпоративное управление, защита инвесторов) | JSON с 3 секциями |
| **1C** | Перечень площадок: какие биржи и торговые системы существуют, их типы, покрытие инструментов | JSON с массивом venues |

**Постобработка:**
1. Агрегация результатов в `jurisdiction_card.json` — единую карточку юрисдикции
2. Извлечение источников и выдержек из `basis[]`
3. Классификация источников по типу документа
4. Очистка артефактов в выдержках
5. Перевод примечаний на русский язык

### 3.2. Level 2 — Площадка

**Один запрос к Parallel API на площадку:**

Исследует структуру площадки: тиры листинга, сегменты, покрытие инструментов, архитектуру листинга. Ответ — JSON со списком тиров.

**Постобработка:**
1. Формирование `venue_card.json` — карточки площадки
2. Формирование `cells_list.json` — перечня ячеек (venue x tier x instrument_class)
3. Извлечение источников и выдержек
4. Нормализация типа площадки (`venue_type`)

### 3.3. Level 3 — Ячейка (детальные требования)

**Три запроса на каждую комбинацию venue x instrument_class:**

| Запрос | Фаза | Секции контента |
|--------|------|----------------|
| **3A** | Допуск | admission_overview, eligibility_requirements, instrument_requirements, sponsor_and_infrastructure, restrictions_and_lock_ups, special_regimes, procedure_and_timeline, disclosure_at_admission |
| **3B** | Поддержание, приостановка, исключение | continuing_obligations (4 подсекции), suspension (4 подсекции), delisting_compulsory (5 подсекций), delisting_voluntary (3 подсекции), terminology |
| **3C** | Мониторинг и enforcement | monitoring_regime (4 подсекции), sanctions (4 подсекции), enforcement_practice (2 подсекции) |

Parallel API возвращает данные на уровне venue x instrument_class (например, «LSE Main Market / equity»). Один ответ может содержать данные по нескольким тирам (например, «Equity Shares (Commercial Companies)» и «Equity Shares (International Companies)»).

**Постобработка:**
1. **Дезагрегация по тирам:** Ответ Parallel содержит массив `tiers[]`. LLM маппит названия тиров на идентификаторы ячеек (cell_id) из cells_list.json. Контент каждого тира сохраняется в отдельную cell-директорию.
2. **Валидация:** Каждый файл проверяется на полноту (completeness_score), соответствие скоупу, наличие источников. Присваивается статус: green / yellow / red.
3. **Извлечение источников и выдержек** из basis[].
4. **Классификация типов источников** и исправление заголовков «Fetched web page».
5. **Очистка артефактов** в выдержках.
6. **Построение матрицы 4x5** — контент распределяется по ячейкам матрицы жизненного цикла (см. раздел 4).
7. **Перевод описаний** секций на русский язык.

### 3.4. Phase 2 — Извлечение параметров

На основе контента L3 (3A/3B/3C) извлекаются количественные параметры листинга:

| Этап | Модель | Что делает |
|------|--------|-----------|
| Pass 1 | gpt-5 | Определяет, какие из стандартных параметров (П01–П23) применимы к данной группе ячеек |
| Pass 2 | gpt-5 | Извлекает конкретные значения параметров для каждой ячейки |
| Перевод | gpt-5-mini | Переводит значения и метки параметров на русский |
| Section keys | Алгоритм | Привязывает параметры к секциям контента |
| Normalize | Алгоритм | Нормализует идентификаторы параметров к кириллице (П01, П02, ...) |

**Стандартные параметры (П01–П23):**

Набор из 23 параметров, покрывающих ключевые количественные требования листинга: free float, минимальная капитализация, количество акционеров, аудиторские стандарты, корпоративное управление, и т.д.

Помимо стандартных, Parallel API может обнаружить дополнительные параметры (ADDITIONAL_1, ADDITIONAL_2, ...), специфичные для конкретной площадки.

### 3.5. Level 4 — Регуляторный анализ

**Один запрос на юрисдикцию** — аналитический обзор регуляторного фреймворка:

| Секция | Что содержит |
|--------|-------------|
| **problems[]** | Проблемы регуляторного фреймворка: что не работает, что критикуется |
| **contradictions[]** | Противоречия между целями регулирования |
| **reforms[]** | Реформы: driver (что движет), opposition (контраргументы), год |
| **parameters_as_tools[]** | Как параметры используются как инструменты регулирования |

Каждая запись содержит описание (EN + RU), источники с URL, и метку для отображения.

## 4. Матрица жизненного цикла

### 4.1. Структура матрицы

Контент L3 организуется в матрицу 4 строки x 5 столбцов:

**Строки — фазы жизненного цикла:**

| Фаза | Описание | Источник данных |
|------|----------|----------------|
| G07_1 — Первичный допуск | Подача заявления, рассмотрение, принятие решения | 3A |
| G07_2 — Поддержание | Обязанности после допуска: пороги, отчётность, управление | 3B (continuing_obligations) + 3C (monitoring, sanctions) |
| G07_3 — Приостановка | Временное прекращение торгов, условия возобновления | 3B (suspension) |
| G07_4 — Исключение | Принудительное или добровольное прекращение допуска | 3B (delisting_compulsory, delisting_voluntary) |

**Столбцы — типы содержания:**

| Тип | Описание |
|-----|----------|
| D01 — Требования | Количественные пороги, качественные критерии |
| D02 — Процедуры | Последовательность действий: подача, рассмотрение, решение |
| D03 — Мониторинг | Кто и как проверяет соблюдение |
| D04 — Санкции | Меры воздействия при нарушениях |
| D05 — Раскрытие | Проспект, отчётность, уведомления |

### 4.2. Построение матрицы

Распределение контента по ячейкам матрицы выполняется в два этапа:

1. **Алгоритмический маппинг** (основной объём): каждая секция L3 однозначно маппится на ячейку матрицы по таблице маппинга.

2. **LLM-маппинг** (пограничные случаи):
   - Санкции из 3C: LLM определяет, к какой фазе относится каждая конкретная санкция (штраф за отчётность → G07_2, делистинг как санкция → G07_4)
   - Мониторинг при приостановке: LLM проверяет, есть ли упоминание мониторинга в период suspension
   - Additional findings: LLM определяет фазу и тип содержания

## 5. Источники и верификация

### 5.1. Типология источников

Каждый источник классифицируется по типу документа:

| Тип | Примеры |
|-----|---------|
| **legislation** | legislation.gov.uk, legifrance.gouv.fr, gesetze-im-internet.de |
| **rulebook** | handbook.fca.org.uk, docs.londonstockexchange.com, rulebook.sgx.com |
| **government** | fca.org.uk, mas.gov.sg, bafin.de, sfc.hk |
| **consultation** | Консультативные документы регуляторов |
| **research** | oecd.org, worldbank.org, академические публикации |
| **other** | Прочие источники |

Классификация выполняется алгоритмически по домену URL.

### 5.2. Выдержки (excerpts)

Выдержки — прямые цитаты из документов-источников, извлечённые Parallel API. Позволяют верифицировать каждое утверждение без перехода к исходному документу.

Выдержки проходят очистку от артефактов поисковых систем (дата-префиксы, маркеры «Read more»).

### 5.3. Уровень уверенности (confidence)

Каждый источник имеет уровень уверенности:
- **high** — источник содержит прямые выдержки, подтверждающие утверждение
- **medium** — источник релевантен, выдержки частично подтверждают
- **low** — источник найден, но выдержки отсутствуют (только URL и заголовок)

### 5.4. Количественные показатели

| Уровень | Источники | Выдержки |
|---------|-----------|----------|
| L1 (юрисдикции) | 555 | 1 244 |
| L2 (площадки) | 78 | 35 |
| L3 (ячейки) | 3 720 | 14 874 |
| L4 (анализ) | 203 | 0* |
| **Итого** | **4 556** | **16 153** |

*L4 источники не содержат выдержек из-за формата запроса (свободный текст).

## 6. Перевод и локализация

### 6.1. Что переводится

| Данные | Откуда | Куда | Модель |
|--------|--------|------|--------|
| Описания секций L3 | `description` | `description_ru` | gpt-5-mini |
| Примечания юрисдикций | `notes` | `notes_ru` | gpt-5-mini |
| Названия тиров | `tier_name` | `tier_ru` | gpt-5-mini |

Интерфейс использует паттерн `field_ru ?? field` — показывает русский перевод, если доступен, иначе английский оригинал.

## 7. Контроль качества

### 7.1. Валидация данных

Каждый файл L3 (3A, 3B, 3C) проходит автоматическую валидацию:

| Метрика | Описание |
|---------|----------|
| **validation_status** | green / yellow / red — общая оценка качества |
| **completeness_score** | 0.0–1.0 — доля заполненных секций |
| **scope_ok** | Соответствие скоупу (venue x tier x instrument_class) |
| **missing_topics** | Список пропущенных тем |
| **suspicious_sources** | Секции без источников |

### 7.2. Идемпотентность

Все шаги пайплайна идемпотентны — повторный запуск не изменяет данные, если они уже обработаны. Это обеспечивает:
- Безопасность повторных прогонов
- Возможность добавления новых юрисдикций без влияния на существующие
- Возобновление после сбоев

### 7.3. Атомарная запись

Файлы записываются через `tempfile + os.replace` — атомарная операция, исключающая повреждение данных при сбое.

### 8.2. Потенциальные расширения

- **L4 выдержки**: Текущие L4 запросы не содержат выдержек из-за формата (свободный текст). Перевод на JSON-формат с output_schema позволит получать excerpts.
- **WGI/WDI метрики**: Интеграция индексов Всемирного банка для сравнительного анализа юрисдикций.
- **Схожие юрисдикции**: Алгоритм определения наиболее схожих юрисдикций по набору параметров.
- **Расширение охвата**: Добавление юрисдикций Emerging Markets (Бразилия, Индия, Южная Корея и др.).

## 9. Техническая архитектура

### 9.1. Стек

| Компонент | Технология |
|-----------|-----------|
| Deep research | Parallel API (processor: pro) |
| LLM (complex) | gpt-5 через LangChain |
| LLM (simple) | gpt-5-mini через LangChain |
| Пайплайн | Python, batch-обработка (max_concurrency=50) |
| Хранение | JSON-файлы на диске, SQLite для интерфейса |
| Бэкенд | Python (FastAPI) |
| Фронтенд | React + TypeScript |

### 9.2. Порядок запуска пайплайна

```
Level 1: EU Framework → 1A → 1B → 1C → Postprocess → Citations → Normalize → Classify → Clean → Translate
Level 2: Prompts → 2A → Postprocess → Citations → Normalize → Classify → Clean
Level 3: Prompts → 3A/3B/3C → Postprocess → Validate → Citations → Classify → Clean → Matrix → Translate
Phase 2: Groups → Pass 1 → Pass 2 → Translate → Section keys → Tier names → Normalize IDs
Level 4: 4A → Citations → Record sources → Labels → Classify → Clean → Translate
```

Каждый уровень может быть запущен независимо. Catchup-скрипты позволяют прогнать отдельные шаги постобработки на уже собранных данных.

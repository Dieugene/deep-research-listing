## 1. Главное: `matrix.json` — теперь доступен (101 ячейка)

### Что это

Файл `matrix.json` содержит данные L3, распределённые по матрице 4x5 (фазы жизненного цикла x типы регулятивного содержания):

**Строки (фазы):**
| ID | Фаза | Источник данных |
|----|------|----------------|
| G07_1 | Первичный допуск | 3A_raw.json |
| G07_2 | Поддержание | 3B continuing_obligations + 3C monitoring/sanctions |
| G07_3 | Приостановка | 3B suspension |
| G07_4 | Исключение | 3B delisting_compulsory + delisting_voluntary |

**Столбцы (типы содержания):**
| ID | Тип |
|----|-----|
| D01_requirements | Требования |
| D02_procedures | Процедуры |
| D03_monitoring | Мониторинг и надзор |
| D04_sanctions | Санкции и enforcement |
| D05_disclosure | Раскрытие информации |

### Расположение файла

```
03_data/countries/{jurisdiction_ru}/level_3/{venue_key}/{cell_id}/matrix.json
```

Существует для **всех 101 ячейки** во всех юрисдикциях.

### Как это влияет на интерфейс

**Проблема, которая решается:** На вкладке "Поддержание" отображалось всё содержимое 3B_raw.json — включая приостановку и исключение. Это не баг фронтенда — данные просто не были разнесены по фазам.

**Теперь:**
- Вкладка **"Допуск"** должна брать данные из `matrix.G07_1`
- Вкладка **"Поддержание"** — из `matrix.G07_2`
- Вкладка **"Приостановка"** — из `matrix.G07_3` (если интерфейс поддерживает 4 вкладки)
- Вкладка **"Исключение"** — из `matrix.G07_4`

**Альтернатива для 3-вкладочного интерфейса (Допуск/Поддержание/Исключение):**
- "Допуск" = G07_1
- "Поддержание" = G07_2 + G07_3 (поддержание + приостановка)
- "Исключение" = G07_4

### Действия для бэкенда

1. Добавить чтение `matrix.json` для tab-view
2. Эндпоинт ячейки должен возвращать данные по фазе из `matrix.json`, а не из сырых `3A/3B/3C_raw.json`
3. Каждая ячейка матрицы (фаза x тип) содержит массив `content[]` с полями `subtitle`, `description`, `source`, `origin_field`
4. `null` означает "не применимо" (например, мониторинг при допуске)

### Действия для фронтенда

1. При переключении вкладок фаз — использовать соответствующий ключ из `matrix`
2. Внутри фазы: 5 типов содержания (D01-D05) можно отображать как подсекции
3. Каждый `content[]` элемент имеет `subtitle` (подзаголовок) и `description` (текст)
4. `source` — URL источника (может быть пустым)
5. `origin_field` — для трассировки: из какого поля schema взяты данные

## 2. Исправлен баг: section_keys для параметров с lifecycle_phase="multiple"

### Проблема

111 параметров со статусом `found` имели пустой `section_keys: []`. Причина: пайплайн не обрабатывал `lifecycle_phase_key = "multiple"` — параметры, которые относятся к нескольким фазам жизненного цикла одновременно.

### Исправление

Добавлен обработчик для `"multiple"`: такие параметры получают `section_keys` из ВСЕХ фаз (admission + continuing + suspension + delisting) — объединение секций, к которым они привязаны.

**Результат:** 32 ячейки обновлены, все `found`-параметры теперь имеют непустой `section_keys`.

### Влияние на интерфейс

Параметры с `lifecycle_phase = "multiple"` теперь имеют полный набор `section_keys`. Фронтенд должен фильтровать `params.filter(p => p.section_keys.includes(currentSectionKey))` — это уже было запланировано (F3 в аудите), теперь данные корректны.

## 3. Пояснение: баги, которые были не багами фронтенда

| Что выглядело как баг фронтенда | Реальная причина | Статус |
|--------------------------------|------------------|--------|
| Смешение тем на вкладке "Поддержание" (приостановка + исключение вместе с обязательствами) | `matrix.json` не был сгенерирован — фронтенд читал сырые данные 3B целиком | **Исправлено** — matrix.json создан |
| Нет источников у большинства секций на "Поддержании" | Citations привязаны к parent-ключу (`suspension`), а фронтенд ищет по subkey (`suspension.procedure`) | Частично баг данных, частично frontend matching |
| Параметры без section_keys (дублируются везде) | Пайплайн не обрабатывал `lifecycle_phase="multiple"` | **Исправлено** — все section_keys заполнены |
